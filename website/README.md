# Menhir docs site

The documentation site for Menhir, a Solid 2.0 app scaffolded with `pnpm create solid@latest` (`with-tailwindcss` template). It uses the library it documents: `menhir` is a `workspace:*` dependency, imported through the same subpath entry points users import.

## How it is built

- **Static output.** `vite build` prerenders the site into `dist/client`, which any static host can serve. Streaming SSR (`ssr: true` in `vite.config.ts`) is not used; hydration and the `solid` export condition are tested in the library instead (#6, #7).
- **Pages.** The home page has the navbar, a hero (the name, the turning ASCII stone in `src/components/stoneFrames.ts`, the tagline, the install command and a link to Getting started), the approach as three numbered cards, a live, styled example of each component, and the credits. The navbar links to `/docs/getting-started` and to `/docs/components`, the list of components with their sizes. Each component has its page at `/docs/components/<name>`. The docs pages in `src/routes/docs/` share the layout in `src/routes/docs.tsx`, which puts a sidebar beside them; a new docs page or component page goes in the list in `src/components/DocsSidebar.tsx`, component pages in its "Components" section.
- **Pages are plain TSX.** Each file in `src/routes` is a page; its path is the URL (`src/routes/docs/components/switch.tsx` is `/docs/components/switch`). There is no MDX or Markdown step.
- **Tailwind CSS 4** styles the site itself. Each component example comes styled two ways, chosen above the live example: with plain CSS, shown unstyled so that only the example's own CSS applies and every other element falls back to the browser's defaults (see `src/App.css`), and with Tailwind CSS, shown with the site's preflight as in an app that uses Tailwind. Under the live example is the chosen version's source, imported with `?raw` so the code shown is the code that runs.
- **Each component page has a Markdown version** for agents, at `/docs/components/<name>.md`, linked beside the page's title and from its `<head>` (`rel="alternate"`), and `/llms.txt` indexes them (https://llmstxt.org). The docs page `/docs/llms-txt` (`src/routes/docs/llms-txt.tsx`) tells users how to give them to an agent. `vite-plugin-component-markdown.ts` makes it with `src/componentMarkdown.ts` from the same data as the page (`src/componentDocs/`), the example's files in `src/examples/<name>/tailwind/` and `css/`, and the size-limit report. The plugin makes `/llms.txt` too, with `llmsTxt` from the same module; its Docs links are written there by hand. The dev server serves both, and the build writes them into `dist/client`, failing as the size plugin does when a size is missing.
- `file-routes.d.ts` is generated by the router plugin on `dev` and `build`. Commit it when routes change.
- **Sizes are generated, never written by hand.** `vite-plugin-sizes.ts` serves the module `virtual:menhir-sizes` (types in `src/menhir-sizes.d.ts`) from the size-limit report in `test/bundle-size/dist/sizes.json`. It exports `sizes`, one row per entry point with its size and budget, which the Components page (`/docs/components`) lists. A component page imports its size from `virtual:menhir-sizes/<name>`, and the build fails if the report has no `menhir/<name>`. `pnpm build` writes a fresh report first, so it builds menhir, and it fails when an entry point is over budget. `vite build` on its own fails without a report. `pnpm dev` and `pnpm test` warn instead, and the pages say "Not measured yet"; run `pnpm --filter @menhir/bundle-size size:json` and restart the dev server to see sizes there.

## Commands

Run from this folder, or from the repo root with `pnpm --filter website <script>`.

| Command          | Does                                             |
| ---------------- | ------------------------------------------------ |
| `pnpm dev`       | Dev server with hot reload                       |
| `pnpm build`     | Size report, then static site in `dist/client`   |
| `pnpm serve`     | Serves the production build                      |
| `pnpm test`      | Vitest in jsdom                                  |
| `pnpm typecheck` | `tsc --noEmit`                                   |
| `pnpm lint`      | oxlint with `eslint-plugin-solid` (`configs/v2`) |

## Adding a component page

Every component ships with its page (PLAN.md section 10). For a component exported as `menhir/<name>`:

1. **Write the example twice**, in `src/examples/<name>/`, importing the component from `menhir/<name>` exactly as a user would. Both versions render the same thing and look the same, in Tailwind's stone colours with a dark variant.
   - `css/<Name>Example.tsx` with a plain CSS file next to it, holding the least CSS that makes the component visible. Write the colours as literal values with a comment naming the stone colour, and use `light-dark()` for the dark variant. Tailwind classes do nothing here; they are reverted.
   - `tailwind/<Name>Example.tsx`, styled with Tailwind classes only, `dark:` for the dark variant.
   - `index.ts` exports the pair as `ComponentExampleProps` (`src/components/ComponentExample.tsx`): each version's component as `render`, and its files, imported with `?raw`, as `files`. See `src/examples/switch/index.ts`.
2. **Write what the page says** in `src/componentDocs/<name>.ts` as a `ComponentDoc` (`src/componentDocs/types.ts`), plain data with no JSX, and add it to the list in `src/componentDocs/index.ts`. The page renders it, and the same data makes the page's Markdown version (see "How it is built").

   ```ts
   import type { ComponentDoc } from "./types";

   export const switchDoc: ComponentDoc = {
     slug: "switch",
     name: "Switch",
     description: "A control that turns a setting on or off.",
     anatomy: "<Switch.Root>\n  <Switch.Thumb />\n</Switch.Root>",
     api: [
       {
         part: "Root",
         description: "The switch itself.",
         props: [
           {
             name: "checked",
             type: "boolean",
             description: "Whether the switch is on.",
           },
         ],
       },
     ],
     keyboard: [{ keys: "Space", action: "Toggles the switch." }],
   };
   ```

3. **Create the page** at `src/routes/docs/components/<name>.tsx` and render `ComponentPage` from `src/components/ComponentPage.tsx` with the data, the size and the example:

   ```tsx
   import { Title } from "@solidjs/meta";
   import switchSize from "virtual:menhir-sizes/switch";
   import { switchDoc } from "../../../componentDocs/switch";
   import ComponentPage from "../../../components/ComponentPage";
   import { switchExample } from "../../../examples/switch";

   export default function SwitchPage() {
     return (
       <>
         <Title>Switch · Menhir</Title>
         <ComponentPage
           {...switchDoc}
           size={switchSize}
           example={switchExample}
         />
       </>
     );
   }
   ```

   - Take `size` from `virtual:menhir-sizes/<name>`, never a number. `pnpm build` fails until the entry point has a size budget in `test/bundle-size/.size-limit.js`. The Components page lists every entry point in the report and links to its page.
   - Link the page from the "Components" section of the sidebar, in `src/components/DocsSidebar.tsx`.

4. **Check it:** `pnpm build` (this also regenerates `file-routes.d.ts` and writes `dist/client/docs/components/<name>.md`), `pnpm typecheck` and `pnpm lint`, then open the page and its Markdown version with `pnpm dev`.
