# Menhir

Unstyled, accessible UI primitives for SolidJS 2.0, with small and measurable bundles.

Status: first release (2026-11-21). Phases 0 and 1 are done and released as 0.1.0, and 0.1.1 is current; phase 2 is under way, with the `floating` layer, Dialog, Alert Dialog, Popover and Tooltip built, and phase 3 has begun with list navigation, typeahead, Navigation Menu, Menu, Context Menu, Menubar, Select and Combobox, and phase 4 with Field (section 9). The tickets of phases 2 and 3 were written out on 2026-11-22, and those of phase 4 on 2026-11-23. What is built is what `packages/menhir/package.json` exports; the READMEs name it, and `test/workspace/readme.test.ts` keeps their lists in step with `exports`. Versions were checked on 2026-11-18 and name availability on 2026-11-19.

## 1. Why this exists

- Solid has fewer component libraries than React, and the established ones were built for Solid 1.x. Libraries that appeared for Solid 2.0 in late 2026 (section 4) carry over the structure and bundle sizes of React libraries.
- Solid 2.0 is now stable (`solid-js@2.0.1`). Every existing library has to migrate, so a library written natively for 2.0 has an opening.
- A recurring complaint about the current Solid options is bundle size: importing one simple component pulls in a large shared layer that does not tree-shake. Menhir treats bundle size as a feature with enforced budgets.

## 2. Goals and non-goals

**Goals**

- Written the Solid 2.0 way. APIs and internals follow Solid 2.0's idioms. Not React APIs with different imports, and not Solid 1.x code with its imports updated.
- Behaviour and accessibility on par with the best React primitives, pinned down by tests (section 8).
- Each component costs only what it uses. Sizes are published per component.
- Near-zero runtime dependencies.

**Non-goals**

- Styling, themes, or a copy-paste component registry. Those can be built on top later. Two exceptions: the color-scheme utility (`menhir/color-scheme/local-storage` and `menhir/color-scheme/cookie`) keeps the reader's light, dark or system choice, and the theme utility (`menhir/theme/local-storage` and `menhir/theme/cookie`) keeps their choice out of the app's themes, since the state and its pre-paint script are the same in every app; how each color scheme or theme looks stays the app's (`docs/adr/0001-color-scheme-utility.md`, `docs/adr/0003-theme-utility.md`). The styling skill (`packages/menhir/skills/menhir-styling`) is not an exception: it ships no CSS in any entry point, only tokens and worked examples for a coding agent to style the app's own components with (`docs/adr/0007-styling-skill.md`).
- Support for Solid 1.x.
- Being a port of, or modelled on, any library. Other libraries may be read for ideas; none sets Menhir's source structure, API, tests or release schedule (section 8).
- Covering every component other libraries have before the first release.

## 4. Landscape

The established Solid component libraries were built for Solid 1.x, and some of them have Solid 2.0 branches that are unreleased or stalled. Several libraries for Solid 2.0 appeared in late 2026; they follow the file structure of a React library and have its bundle sizes (a Switch is 18 to 22 kB minified). Styled, copy-paste layers built on the existing libraries are potential consumers of Menhir, not competitors.

The Solid 2.0 libraries were evaluated by reading their code on 2026-11-19 (#1), and those on npm had their bundles measured. None of them competes on bundle size, and the one viable to contribute to has a goal that conflicts with section 8, so the decision is to continue with Menhir (section 12, question 1).

### Browsers

Decided on 2026-11-22 (#94; ADR 0006): **Baseline Widely available** on the date of each release, plus the exceptions below, each with its reason: the `popover` attribute, `focus({ preventScroll: true })` (added on 2026-11-23, #97), and `focus({ focusVisible: false })` (added on 2026-11-25, #148).

- A feature is used without a fallback once it is Widely available: in every core browser (Chrome, Edge, Firefox and Safari, on desktop and on mobile) for 30 months. Before that it is not used, and no fallback is shipped for it (section 6, rule 6).
- **The exception:** `popover`, with `popovertarget`, `:popover-open` and the `toggle` events of a popover. It has been Newly available since 2025-01-27 and is Widely available from 2027-07-27. The gap is iOS Safari 17.0 to 18.2, where a tap outside does not close a popover; everything else works there. It is worth the exception because without it Popover, Tooltip and every menu ship a portal, a stacking order and their own light dismiss (section 8, "What the browser does for popups").
- **The exception for `focus({ preventScroll: true })`** (#97): the option is not Baseline: Chrome and Firefox on Android lack it, and there it is ignored, so focus scrolls the item into view. List navigation uses it where the pointer moves a list's active item, and a touch, the usual pointer on Android, never moves it. Everywhere else it stops the list jumping under the pointer. No fallback is shipped (section 6, rule 6). `floating/list-navigation/README.md`, "Decisions", has the details.
- **The exception for `focus({ focusVisible: false })`** (#148): Newly available since 2026-02-14 (Chrome and Edge 145, Firefox 104, Safari 18.4), Widely from 2028-08-14. A Slider's Track focuses its input when pressed, and Chromium, Firefox and WebKit all match `:focus-visible` for a script's focus after a canceled press (tried on 2026-11-25 in Chromium 159, Firefox 159 and WebKit 27.2), so without the option every press would show the focus ring in every browser. A browser without it ignores it and shows the ring after a press; nothing else changes, and no fallback is shipped (section 6, rule 6). `src/slider/README.md`, "Decisions", has the details.
- Status is read from the `web-features` package (3.47.0 on 2026-11-22), which computes Baseline from MDN's browser-compat-data (8.1.10 on the same day). A decision that depends on support records the date it was checked.
- Tests run in Chromium. The spike in #94 also ran in Playwright's Firefox and WebKit (Chromium 159, Firefox 159, WebKit 27.2): these are current engines, so they show how a feature behaves, not how far back it works.

Solid 2.0 changes that affect a component library (confirm against the official migration guide, `MIGRATION.md` in the solid repo, and v2.solidjs.com):

- `createEffect` is split into a compute phase and an apply phase.
- `onMount` is replaced by `onSettled`.
- Updates are batched per microtask: a read returns the old value until the flush, and `flush()` applies pending updates now. `batch` is gone.
- Writing a signal inside a component body, memo or effect compute throws in development; `untrack` does not exempt it. Writes belong in event handlers, `onSettled` or actions.
- A reactive read at the top of a component body, or of a `<Show>`/`<For>` callback, is reported in development unless wrapped in `untrack` as a deliberate one-time read.
- Writes in one frame are applied together, so async work one of them starts holds the others. `onFlush` keeps a write out of that hold (API conventions, section 8).
- The `use:` directive is removed in favour of ref factories.
- `<Index>` is replaced by `<For keyed={false}>`.
- Async is part of the reactive graph; Suspense is reworked.
- `render` and the JSX import source come from `@solidjs/web`.

## 6. Bundle-size rules

These are structural and must hold from the first commit.

1. **One entry point per component.** `menhir/dialog`, `menhir/switch`, and so on, declared in `exports`. No root barrel as the main way in.
2. **Unbundled ESM, `"sideEffects": false`.** One output file per source module. No code that runs at import time. Development-only code, such as warnings, sits behind `isDev` from `@solidjs/web`: Solid's production builds define it as a constant `false`, and Rolldown drops the branch and whatever only it imports (measured on 2026-11-19 on `createControllableSignal`: 302 B minified in production, 573 B in development).
3. **No `Object.assign` compound components.** Use namespace re-exports so unused parts are dropped. Rollup and Rolldown drop them; esbuild keeps the whole namespace (measured on 2026-11-19), so measure part-level budgets with Rolldown:
   ```ts
   // dialog/index.ts
   export * as Dialog from "./index.parts.ts";
   // dialog/index.parts.ts
   export { DialogRoot as Root } from "./root/DialogRoot.tsx";
   export { DialogTrigger as Trigger } from "./trigger/DialogTrigger.tsx";
   ```
   The build has to keep that re-export as written; see "Build" in section 7.
4. **Strict layers.** Enforced by an import-boundary lint rule.

   | Layer             | Contains                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               | May import                                 |
   | ----------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------ |
   | `core`            | Prop merging, controlled/uncontrolled signal, polymorphism helper, the props of parts that are buttons and toggle buttons, the hidden input of a control that is a button (`hiddenInput.tsx`, #147), a value one part registers once mounted for another to read (`slot.ts`), a part's value along a range, a value that lists items, a group's roving focus, the utilities' saved preference, the context through which Form hands its errors to each Field (`formContext.ts`, #144). Ids are Solid's `createUniqueId` (#13)                                                                                          | Nothing internal                           |
   | `floating`        | Positioning (`createPosition` and one file per middleware), dismissal (one file per way of closing, and the reasons a popup closed), focus (the Tab wrap of a modal popup, overrides of initial and return focus, the tabbable search the wrap needs), scroll lock (`overflow: hidden` on `<html>` while a modal popup is open), presence (showing a popup, and hiding it once its exit animations have ended), hover intent (the delays, the safe area to the popup, delay groups, one file each), list navigation, typeahead. No portal: popups are in the top layer (section 8, "What the browser does for popups") | `core`, `@floating-ui/dom`                 |
   | Simple components | Switch, Toggle, Checkbox, Checkbox Group, Tabs, etc.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   | `core`, the simple component it builds on  |
   | Popup components  | Dialog, Popover, Menu, Select, etc.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    | `core`, `floating`, the popup it builds on |

   A popup that builds on another imports that popup too, and no other: Alert Dialog re-exports Dialog's Root, Trigger, Title, Description and Close and calls the code of its Popup (#32). `popupBases` in `packages/menhir/layers.ts` names each pair, and the lint rule allows those imports only, so the layers stay a tree and an app that uses both popups pays for the shared parts once. Decided on 2026-11-22 (#32), over two other options: putting the shared parts in `floating` would make the layer that holds behaviour hold components, each with a module budget of its own, and a copy in each popup would make an app with both pay twice. Context Menu re-exports Menu's items, groups and submenus, and its Popup calls Menu's with the point as its anchor, so Menu needed no split into a render function (#100). Menubar re-exports Menu's Popup, items, groups and submenus and wraps its Trigger, and sets three fields of a menu's state that Menu reads: the opening that leaves focus on the bar, the arrow keys' path along the bar, and a press after hover (#101). Select builds on no popup: focus stays on its Trigger, so it shares list navigation and typeahead with Menu through `floating`, and none of Menu's parts (#102). Autocomplete re-exports Combobox's Trigger, Clear, Popup, List, Group, GroupLabel and Status, provides Combobox's context from its own Root, and its Root, Input and Item call the code they share with Combobox's (#104).

   A simple component may build on another the same way, named in `simpleBases` in `packages/menhir/layers.ts` and allowed by the same lint rule: Checkbox Group renders Checkbox's Root for its Item and Parent and re-exports its Indicator (#146). The base reads no context of the component built on it, so an app with Checkbox alone bundles nothing of the group (`test/bundle-size/checkboxGroupModules.test.ts`), and an app with both pays for Checkbox once. Decided on 2026-11-24 (#146), over a copy of Checkbox in the group, which an app with both would pay for twice, and over a group context read by Checkbox, which every Checkbox would pay for.

5. **Near-zero dependencies.** `@floating-ui/dom` only. Use built-in `Intl` for number and date formatting.
6. **Expensive behaviour is a part, not a flag.** Behaviour a component can do without, such as each positioning middleware, is composed in, so apps that don't render it don't ship it. Behaviour a component always needs ships with it, never behind a flag: every modal popup locks the page's scroll, since a page that scrolls behind a modal popup is a bug, not a choice (#31). Behaviour the browser does is not shipped at all (section 8, "What the browser does for popups").

The package manifest, in the shape built in the build spike (#6). It lists one subpath per built component, such as `./switch`, and one per utility and storage, such as `./color-scheme/cookie`; `./dialog` shows how each further component is added:

```json
{
  "name": "menhir",
  "type": "module",
  "sideEffects": false,
  "exports": {
    "./dialog": {
      "types": "./dist/source/dialog/index.d.ts",
      "solid": "./dist/source/dialog/index.js",
      "import": "./dist/dialog/index.js"
    },
    "./switch": {
      "types": "./dist/source/switch/index.d.ts",
      "solid": "./dist/source/switch/index.js",
      "import": "./dist/switch/index.js"
    }
  },
  "dependencies": { "@floating-ui/dom": "^1.8.0" },
  "peerDependencies": { "solid-js": "^2.0.0", "@solidjs/web": "^2.0.0" }
}
```

The `solid` condition points at uncompiled JSX and must come before `import`: compiled DOM output cannot hydrate and cannot render on the server, so SSR apps need the source. Confirmed in the build spike (#6), in two ways:

- **The Solid 2.0 library guide says so.** It is the "Building a library" section of the `@solidjs/vite-plugin` 3.0.1 README. It prescribes JSX source under `solid`, listed before `import`, with `solid-js` and `@solidjs/web` as peers. The plugin adds `solid` to Vite's `resolve.conditions`, and bundles every dependency that has a `solid` export into the SSR build instead of leaving it external.
- **Removing it breaks SSR.** With the `solid` key deleted from `menhir`, the fixture app in `test/ssr-app` fails to render with "Client-only API called on the server side", because the server then gets the DOM build.

The entry of a component is a `.ts` file with no JSX, so its `solid` target ends in `.js`. The `.jsx` files are the modules it imports.

No separate server build under `node`/`worker`/`deno`, which some Solid libraries ship. It would serve only an app that renders on the server without compiling its dependencies, which is not a setup the guide describes: an app on the Solid plugin always compiles the `solid` source. Add one if a user turns up with such a setup.

### Enforcement

- A size budget per entry point in CI (size-limit or similar). A pull request that exceeds a budget fails.
- Per-component sizes published in the docs.
- A CI test that bundles a single simple component and asserts nothing from `floating` is included.

Built in #9, in `test/bundle-size` (its README has the details):

- `.size-limit.js` holds one budget per entry point. `size-limit` 14 measures each with `@size-limit/rolldown`: an app that imports the entry point and uses every part of it, minified and gzipped, Solid left out. The size is that of a production app: a Rolldown plugin (`productionConstants.ts`) defines `isDev` and `isServer` as `false`, as Solid's production build does, so the code behind them is not counted (rule 2; #46). Rolldown because esbuild keeps a whole namespace. `size.test.ts` fails if an entry point in `exports` has no budget or is over it.
- `pnpm size:json` writes the same results to `dist/sizes.json`, from which the docs site generates its size table and each component page's size (#38, `website/vite-plugin-sizes.ts`).
- The bundle-size page also shows each component's size in other libraries, measured the same way with each library's framework left out (`comparison.ts`). These sizes are shown, not enforced. Its last row is of the components imported together, so that shared code is counted once. The page says these are sizes only: the libraries differ in API and in what each component includes.
- `floating.test.ts` bundles each simple component's entry point, such as `menhir/switch`, alone with Rolldown (every entry point in `exports` except the popups that `packages/menhir/layers.ts` lists for the lint config too) and fails if the bundle has a module from `floating` or an import of `@floating-ui/*`.
- `checkboxGroupModules.test.ts` bundles `menhir/checkbox` alone and fails if the bundle has a module of Checkbox Group, which builds on it (rule 4, #146).
- `popupModules.test.ts` does the same for each popup, against what that popup must not bundle (`popupModules.ts`): `menhir/dialog` and `menhir/alert-dialog` bundle no `@floating-ui/*`, no positioning and no hover. A row is checked once its popup is in `exports`, and a fixture popup proves the check reports a module it should not bundle (#95).
- `floatingSize.test.ts` holds each module of the `floating` layer to its budget in `floatingBudgets.ts` (below), and fails if a folder in `src/floating` has none.

### The `floating` layer

Set up on 2026-11-22 (#95). `packages/menhir/src/floating/README.md` lists the modules, one folder each, and the layer's rules. `floatingModules` in `packages/menhir/layers.ts` lists the same folders for the checks in `test/bundle-size`. Three decisions:

- **Internal**, as `core` is: no entry point in `exports`, so a module can change without a release note until 1.0. Apps and styled layers use the popup components. `test/package/build.test.ts` exempts both layers from its `exports` check. Revisit after Phase 2 if a styled layer asks to build its own popups.
- **A budget per module file, measured and not published.** A module has no entry point, so `test/bundle-size/floatingBudgets.ts` gives one to each file a popup imports, keyed by its path under `dist/floating`. `floating.size-limit.js` measures each the way `.size-limit.js` measures an entry point: an app that imports it and uses all of it, minified and gzipped, Solid left out, `@floating-ui/dom` counted. These sizes are not in `dist/sizes.json`, so the docs site does not show them; each module's README records its own. So that a module is built before any popup imports it, `vite.config.ts` makes every file in `src/floating` an entry.
- **No shared stack of open popups.** Since #94 the top layer is the stack: a modal `<dialog>` and an `auto` popover nest by themselves, only the topmost dialog is not inert, and the page stops scrolling with `overflow: hidden` on `<html>` (#28 sets it inline, counted). A module asks the browser (`:modal`, `:popover-open`, the event's target). A Tooltip's Escape listener calls `preventDefault()`, which stops the close request, so a dialog below it stays open. If a module ever needs a stack, it lives in `floating/stack/`, created in the browser on first use and never at import time, since module state is shared between requests on the server.

- **Dismissal is one file per way of closing** (#26): `dialogClose.ts` (Escape and other close requests on a modal dialog, a refused close opened again), `outsidePress.ts` (a press on a dialog's backdrop), `popoverClose.ts` (the reason an `auto` popover closed, a refused close shown again) and `escape.ts` (Escape for Tooltip's `manual` popover, and Navigation Menu's in-flow Panels, #105). Alert Dialog bundles no `outsidePress`, and Tooltip only `escape`: `test/bundle-size/popupModules.ts` names a forbidden file of a module as well as a whole folder. `dismissal/README.md` records the decisions and each file's size.

- **Focus is one file per behaviour** (#27): `tabWrap.ts` (Tab and Shift+Tab cycle inside the topmost modal `<dialog>`), `tabbable.ts` (the tab stops inside an element, framework-free, which only the wrap imports), `initialFocus.ts` and `returnFocus.ts` (where focus goes once a popup has opened, and once it has closed). Dialog and Alert Dialog are always modal and call `createTabWrap` from their Popup. **A modal Popover is left out** (decided on 2026-11-22, #33): a popup that keeps focus inside until it closes is a Dialog. A `modal` flag would ship the wrap and the scroll lock in every app that uses Popover, and a part or a ref factory over a widened `createTabWrap` would be a second way to build a Dialog, so `createTabWrap` stays a modal `<dialog>`'s. `focus/README.md` records the decisions and each file's size.

- **Scroll lock is one file** (#28): `scrollLock.ts` sets `overflow: hidden` on `<html>` while a modal popup is open, counted so that nested popups unlock the page when the last one closes, and puts the page's own inline styles back. A page with a scrollbar gets its width as `padding-right` on `<html>`, so the content does not move, and as `--hidden-scrollbar-width`, which a `position: fixed` element uses to keep its place; a page with `scrollbar-gutter: stable` gets neither. The lock does not set `scrollbar-gutter` itself, since it is Widely available only from 2027-06-11 (section 5). The page unlocks once the popup has closed, after an exit animation (#96), not when its state turns false. A page that scrolls in another element needs no lock: a popup in the top layer chains its scrolls to the viewport (Chromium). On iOS Safari (26.5, tried on a device) a drag on the backdrop scrolled the page all the same, so while open the popup gets `overscroll-behavior: contain` and, if it does not scroll itself, `touch-action: pinch-zoom`, checked again as it changes size: a popup that overflows keeps its own `touch-action`, since Chromium would no longer scroll it by touch. Zoomed in, the popup then pans with two fingers. Chrome on iOS still scrolls the page from a drag on a dialog's text (#114). Only modal popups import it; `popupModules.ts` checks that Popover and Tooltip do not. `scroll-lock/README.md` records the decisions, what was tried on iOS Safari, and the size.

- **Presence is one file** (#96): `presence.ts` (`createPresence`) shows a popup when its state turns open, with `showModal()` for a `<dialog>` and `showPopover()` otherwise, and once it turns closed keeps it shown until the animations and transitions running in it, its descendants and its `::backdrop` have settled, then calls `close()` or `hidePopover()`; with none running it hides at once, with no timer. Infinite and paused animations do not count. While it leaves the popup is `inert`, except a popover that holds focus, since hiding a popover returns focus to its trigger only from inside it; a dialog's `close()` returns focus wherever focus is. Opening again cancels the exit. A closed popup stays in the document, `display: none` by the browser, so there is no `<Show>` and no "mounted" state in Solid. Focus returns and the page unlocks on the `close` or `toggle` event this fires (#27, #28). A popover the browser hides itself, by light dismiss, Escape or its `popovertarget`, is hidden at once, since `beforetoggle` cannot be cancelled on closing; Popover (#33) decided that is enough: Escape and a press outside hide it at once, and its Trigger and Close, which close it through its state, wait for the exit animation. It stays in `floating`: Collapsible and Accordion animate their panels with CSS alone. `presence/README.md` records the decisions and the size.

- **Hover is three files** (#30): `safeArea.ts` (once the pointer has left the trigger or the popup, whether it is still on its way to the other: every point on a line from where it left to the other's box; plain DOM, no timers, so a submenu uses it without the delays), `hover.ts` (`createHover`: opens after `delay`, closes `closeDelay` after the pointer has left both through the safe area; a mouse or a pen opens it, a touch does not) and `group.ts` (`createHoverGroup`: once one popup of a group is open, the next opens at once and the first closes). Grouping is a part that provides the group through context, not module state, which would group every popup of the app, run for apps that never group and be shared between requests on the server. `popupModules.test.ts` checks that the safe area alone bundles no timer and that `hover.ts` bundles no group. `hover/README.md` records the decisions, what Chromium does when the page scrolls under a still pointer or the pointer leaves the window, and each file's size.

- **Positioning is the only folder that imports `@floating-ui/dom`** (#25), and the build leaves the import in place (`vite.config.ts`), so an app's bundler resolves the one copy. `createPosition.ts` holds `computePosition` and `autoUpdate`, and each middleware is a file of its own (`offset`, `flip`, `shift`, `size`, `arrow`, `hide`), so a popup bundles only those it passes (rule 6). `positioning/README.md` records the size of each file and what each middleware adds.

- **List navigation is two files over a shared one** (#97): `roving.ts` (`createRovingList`, focus moves to the active item, for Menu) and `activeDescendant.ts` (`createActiveDescendantList`, focus stays on an element that names the active item in `aria-activedescendant`, for Select's Trigger, #102, and Combobox's input), both over `listNavigation.ts` (the items in document order, the active item, arrow keys, Home and End, wrapping, right to left, the pointer, scrolling into view). The parts call its handlers from their own events. Each item has its own active signal, set and cleared on each move, so a move re-runs two items, not several hundred, with no store: `createProjection` did the same with Solid's store engine, which cost an app that has no store 8,198 B gzipped (measured on 2026-11-23, Solid included), and was dropped on review; `popupModules.test.ts` checks that no file imports the store engine. It reports the keys into an item and out of the list for a submenu, which Menu (#99) opens and closes, and acts only on keys from its own items or from the element that hands them over, so a submenu's keys, which bubble through its parent item, move only the submenu; it opens nothing itself and has no stack. Typeahead (#98) gets its items, active item and move from the component, and neither folder imports the other. The key mapping stays apart from `core/rovingFocus.ts`: sharing it grew Tabs and Toggle Group by 16 B to 55 B, which triage ruled out. `focusgroup` is not Baseline. `popupModules.test.ts` checks that each of the two files bundles neither the other nor typeahead, and that Dialog, Alert Dialog, Popover and Tooltip bundle none of it. `list-navigation/README.md` records the decisions and each file's size.

### Package shape

Decided on 2026-11-19 (#3): one `menhir` package with one subpath export per component. No `@menhir/*` packages.

Reasoning, by consideration in #3:

- **Release overhead.** One version, one changelog, one publish. With separate packages, every `core` change means releasing every package that depends on it. The benefit of separate packages, independent semver per component, is worth little before 1.0, when components change together.
- **Duplicate shared code.** Separate packages share `core` as a dependency. An app that resolves two versions of it ships two copies, and parts built against different copies do not share context. With one package, all components in an app come from the same `menhir` version, so they share one `core`.
- **Tree-shaking.** Bundlers drop unused modules, not unused packages. With unbundled ESM, `"sideEffects": false` and one entry per component (rules 1 and 2), importing `menhir/switch` includes only the modules reachable from that entry, the same result as a separate `@menhir/switch` package. The checks under Enforcement test this.
- **Keeping `floating` out.** `@floating-ui/dom` is a regular `dependency` of `menhir`. Every install downloads it (174 kB unpacked in 1.8.0), but only `floating` modules import it, and only popup entries import `floating` (rule 4). An app that uses only simple components never bundles it. An optional peer dependency would save the download but make every popup user install it by hand.
- **Consumers.** A styled layer installs one package and imports from subpaths, and keeps one version current instead of a set in step. It should list `menhir` as a peer dependency, so that an app using two styled layers still resolves one copy of `menhir`.

Costs accepted:

- An app cannot upgrade one component without the rest. Revisit if users ask for it after 1.0.
- Subpath types need `moduleResolution` set to `bundler`, `node16` or `nodenext`. Consumers on `node10` (`node`), which TypeScript 7 has removed, are not supported; no `typesVersions` fallback is shipped.

### Build

Decided in the build spike (#6), on a throwaway two-part Switch. `pnpm build` in `packages/menhir` runs both steps:

- `vite build` (`vite.config.ts`) writes the compiled `import` entries to `dist`, one file per source module (`preserveModules`), with `solid-js` and `@solidjs/web` external.
- `tsc -p tsconfig.build.json` writes the JSX source and the types to `dist/source`. It covers only `src`.

A component is added by adding its subpath to `exports` in `package.json`, the only list of components: `vite.config.ts` reads its entries from there. Its size budget is a line in `test/bundle-size/.size-limit.js`; `pnpm test` there fails until it is added. `pnpm test:package` builds, then checks `dist` (`test/package`): one compiled file, one source file and one `.d.ts` per module, an `exports` entry for every folder in `src` with an `index.ts`, and that a bundler drops an unused part. It is kept out of the default `vitest` run so that watch mode does not rebuild.

What the spike found:

- **Rolldown breaks rule 3 unless told otherwise.** Rolldown 1.2 compiles `export * as Switch from "./index.parts.ts"` into an object of getters, and no bundler can drop an unused part from an object: an app using only `Switch.Root` also got `Switch.Thumb`. A small plugin in `vite.config.ts` builds each `index.parts.ts` as an entry of its own and leaves the import of it external, so `index.js` keeps the namespace re-export. tsdown was not tried; it bundles with Rolldown too, so it probably needs the same fix.
- **Relative imports name the source file**, such as `./root/SwitchRoot.tsx`. `rewriteRelativeImportExtensions` turns that into `.jsx` or `.js` in the emitted source. Extensionless imports fail `attw` under `node16` resolution.
- **`attw` runs with `--profile esm-only`.** `node10` cannot resolve subpath exports and the package has no CommonJS build (section 6, "Costs accepted").
- **Hydrate tests need two compiles of the same JSX**, one for the server and one hydratable one for the DOM, each against its own build of Solid. A test file gets only one. So `*.hydrate.test.tsx` files run in a `hydrate` Vitest project whose plugin compiles hydratable DOM code, and its global setup (`test/ssr/renderServer.ts`) starts a Vite SSR server that renders fixtures over HTTP. A test calls `renderOnServer("/path/to/Fixture.tsx")`, which returns an element holding the server HTML, then `render(() => <Fixture />, { hydrate: element })`. It works in jsdom and in Chromium.
- **Vitest projects that compile differently must not share a transform cache.** Vitest 5's `fsModuleCache` is keyed by file, not by plugin options, so the `hydrate` project has its own `fsModuleCachePath`. Sharing it gave the hydrate test the `client` project's non-hydratable output.
- **`test/ssr-app`** is a minimal SSR app that depends on `menhir` like an installed app. Its test builds it for server and client, renders the server bundle in Node and hydrates the result with the client bundle. `test/package` in `packages/menhir` checks the built package: one file per module, the order of the export conditions, and that an unused part is dropped.

## 8. Sources and approach

Menhir is written the Solid 2.0 way. What decides how a component is built, in this order; an earlier one wins when two disagree:

1. **Solid 2.0 idioms** decide the API and the internals: [AGENTS.md](AGENTS.md), `node_modules/solid-js/CHEATSHEET.md`, the migration guide and v2.solidjs.com.
2. **The WAI-ARIA Authoring Practices** pattern for the component decides its roles, states and keyboard behaviour.
3. **Size.** A component costs only what it uses (section 6). Between two ways of meeting 1 and 2, the smaller one wins, and extra behaviour has to be worth its bytes.
4. **Other libraries** may be read for ideas, such as browser and assistive-technology fixes the pattern does not spell out. None is a model for Menhir's source structure, API or tests. They are credited in one place, the docs site's home page. Elsewhere a library is named only where it is the subject: the size comparison (`test/bundle-size`), a manual behaviour comparison (`test/manual`), or a look of the styling skill, which is named after what it looks like (`docs/adr/0007-styling-skill.md`). A library is never named as the reason for a Menhir decision.

How this applies to each component:

- **Write behaviour; never translate source.** React re-runs a component on every change while Solid runs it once, so translating hooks loses reactivity and mistimes effects. Solid 1.x code has the same problem: effects, ownership and the props helpers changed in 2.0.
- **Assemble the test list first.** Start from the cases the WAI-ARIA Authoring Practices pattern requires, then add browser and assistive-technology behaviour, forms, SSR and hydration, and Menhir's own conventions. Write each test against Menhir's API.
- **Set the size budget with the component.** Its entry point gets a budget in `test/bundle-size` when it is added, and it imports only the layers it is allowed to (section 6).
- **Record the sources.** For each component, record the WAI-ARIA pattern and the date it was read, and check the pattern for changes at each release ([CONTRIBUTING.md](CONTRIBUTING.md)).
- **Licences.** Menhir's code and tests are its own; reading another project for ideas needs no notice. Code or test bodies are not copied from other projects. If that is ever unavoidable, the source's licence notice goes into LICENSE with the change. A look of the styling skill reproduces another library's styles on purpose; that library's licence goes in the look's own `LICENSE` (CONTRIBUTING, "Copyright notices").

### Polymorphism

Decided on 2026-11-19 (#11): every part that renders an element takes a `render` prop, a function that receives the element's props and returns the element. There is no `as` prop.

```tsx
// The default element.
<Switch.Root class="switch" />

// Another element. Attributes only that element has go here.
<Switch.Root class="switch" render={(props) => <a {...props} href="/settings" />} />

// A component that spreads its props onto an element.
<Dialog.Trigger render={Button} />
<Dialog.Trigger render={(props) => <Button {...props} variant="ghost" />} />
```

In Solid a function from props to JSX is a component, so `render` is "the component to render this part with". It covers what an `as={Button}` prop does; only the tag-name form, `as="a"`, is left out.

Why not `as`, which the first two sources in the order above both point to. Passing a component as a prop is as much a Solid idiom as `as` is, so the order does not settle it, and size does (section 2, "Each component costs only what it uses"). Solid 2.0 documents the `as` pattern, `dynamic(() => props.as, { static: isStatic(props, "as") })`, and it worked in the prototype. But a tag name can only be rendered by `dynamic`, and the `@solidjs/web` types say what that costs: "one `dynamic` on a page retains the element runtime (create/claim, `spread`, the namespace tables) for everyone". A bundler cannot tell whether a tag name ever arrives, so every app that imports a Menhir part would pay it, whether or not it uses `as`. That is a flag, not a part (section 6, rule 6), and it is three times the size of the Switch budget (the budgets leave Solid out, so no budget would catch it). `@solidjs/router` 2.0.0 uses only `dynamicComponent`, the variant without the tag path, so an app with the router does not already have it. The same cost rules out offering both props, and a `render` that also takes a tag name.

Solid's creator, Ryan Carniato, makes the runtime case against `as` as a library pattern (spoken remarks in https://www.youtube.com/watch?v=SpJbyFzF6Ao, quoted from a transcript on 2026-11-19). It is "generally more expensive for everyone and it's especially more expensive for solid", because it introduces dynamic components and dynamic spreads, which revert fine-grained updates "to basically shallow diffing". `render` removes the dynamic component. It does not remove the spread: a part still spreads one merged props object onto its element, as any part that forwards arbitrary props does. Measured in #13 (below): in Solid 2.0.1 one element's dynamic attributes share one update with or without a spread, so the spread costs no more than the same attributes written in JSX. What does cost is building the spread object inside the JSX, and `dynamic`.

Measured on a throwaway Switch root, built with Vite 8 and minified (`solid-js` and `@solidjs/web` 2.0.1). "Solid's runtime" is the growth of a whole app, with Solid bundled in, over the same part with a fixed element:

|                                  | `as` through `dynamic()`             | `render` function              |
| -------------------------------- | ------------------------------------ | ------------------------------ |
| Menhir's own code, per part      | +14 B                                | +80 B (25 B gzipped)           |
| Solid's runtime, once per app    | +4.6 kB (1.6 kB gzipped)             | +0.1 kB                        |
| Server render, then hydration    | Adopts the server's element          | Adopts the server's element    |
| Dev diagnostics                  | None                                 | None                           |
| Types                            | A generic on every part; infers well | No generics                    |
| Element swapped while mounted    | Yes                                  | No, `render` is read once      |
| Consumer writes, for another tag | `as="a"`                             | `render={(p) => <a {...p} />}` |

Both were tested with a default element, another tag and a component, in jsdom and through the `hydrate` project.

What the choice costs:

- The common case is longer to write than `as="a"`.
- Styled layers written for a library with an `as` prop replace `as={Button}` with `render={Button}`, and `as="a"` with a function. Layers written for a library whose `render` takes a tag name, a JSX element, a `{ component, props }` descriptor or a `(props, state)` function turn it into a function of props.
- The element cannot change while the part is mounted. A consumer who needs that calls `dynamic` in their own render function, and only their app pays for it.

Rules for parts and for the docs:

- **Props go on the part.** `class`, `style`, `ref`, event handlers and `data-*` attributes are passed to the part, which merges them with its own (`core/mergeElementProps.ts`: both handlers run, the consumer's first; `class` and `style` combined; refs composed) and hands the render function one props object. The render function spreads it and adds only what the part cannot know, such as `href`.
- **Nothing cancels the part's handler.** Both always run, and `preventDefault()` only stops the browser's default action. A consumer who needs to stop a part's behaviour controls its state: a controlled part only asks for a change (`createControllableSignal`), and a popup passes a reason to its open-change callback (#26). Decided on 2026-11-19. If a case appears that neither covers, add an explicit opt-out, not a `defaultPrevented` check, which would cancel the part for consumers who only meant the browser.
- **The spread is not a merge.** Next to `{...props}`, the later attribute wins: a handler written after the spread replaces the part's handler, one written before it is never called, and `class` behaves the same way. Refs are the exception: one written before or after the spread runs, and so does the part's (`src/core/renderElement.test.tsx`).
- **`undefined` is a value.** In `merge`, a consumer's `undefined` replaces the part's own value, as for any prop. A wrapper that forwards `id={props.id}` without an id therefore removes a generated `id`; a part that needs its own value whatever the consumer passes keeps it out of the merge, for example `id={props.id ?? generated}` in its own props, with `id` omitted from the consumer's.
- **Merge in the part's body**, never inline in a spread (`{...mergeElementProps(own, props)}`). The compiler tracks a spread's expression, so an inline call runs the whole merge again on every change of any prop it reads.
- **`render` is read once**, untracked, when the part is created, as an event handler is (AGENTS.md: "`onClick={cond() ? a : b}` binds once").
- **The props object is reactive.** It is a `merge` view with getters, so the render function spreads it or reads from it in JSX, and never destructures it (AGENTS.md rule 1).
- **No state argument yet.** A part's state reaches the render function as the `data-*` and `aria-*` attributes in `props`. A second argument can be added later without breaking anything, once #12 has settled what state a part exposes.

### API conventions

Decided on 2026-11-20 (#12), worked out on Switch (#15), the first component. Generated ids were decided on Collapsible (#22), the first component that links its own parts (below). Revise after the first two or three components.

- **Form controls are native buttons.** Switch's Root is a `<button type="button" role="switch">`, then a visually hidden `<input type="checkbox" aria-hidden="true" tabindex="-1">` for forms. The button gives keyboard support (Enter on key down, Space on key up), focus, `disabled` and labelling by a `<label>` without code, and the label works in the server HTML before hydration. A `<span role="switch">` would re-implement the button and compute `aria-labelledby` after mounting; a hidden native checkbox as the control would put focus on an invisible element and need more parts. The same applies to Checkbox (`role="checkbox"`) and Radio. A control whose WAI-ARIA pattern names only Space, as Checkbox's does, cancels Enter on key down, which also matches the native control; decided on 2026-11-21 (#18).
- **`render` on such a part must render a `<button>`**, and on Toggle, a `<button type="button" aria-pressed>` with no hidden input, since a toggle button is not a form control (#16). Development builds warn otherwise. No `nativeButton` flag: emulating a button would ship in every app (section 6, rule 6).
- **Parts.** Only what a native element cannot do. Switch is `Root` and `Thumb`; labels are native `<label>` elements. Description and error message parts belong to Field (#141), shared by every control ("Fields" below).
- **Controlled state.** `<state>`, `default<State>` and `on<State>Change`: `checked`/`defaultChecked`/`onCheckedChange`, `pressed`/`onPressedChange`, `open`/`onOpenChange`, `value`/`onValueChange`. Never `onChange`, which is a DOM event in the JSX types and which `mergeElementProps` treats as a handler. An empty controlled value is `null`, since `undefined` means uncontrolled (`createControllableSignal`); a value that lists items, such as Toggle Group's pressed items or Accordion's open ones, is an array in every mode, and `[]` when empty (#17, #23; `core/listValue.ts`).
- **A part's own state is not held by its consumer's async work.** An uncontrolled part writes its state in `onFlush`, after the event's flush, so it changes even when the change callback starts a fetch or a transition; written inline, it would wait for that work to settle (Solid's RFC on reactivity, batching and effects, "Keeping a write out of another update's hold"). `createControllableSignal` does this. A controlled part's value is the consumer's, and so is its timing. Tests await `afterFlush()` from `#test-utils` before asserting such a change; `flush()` does not run `onFlush` callbacks. Decided on 2026-11-20.
- **Change callbacks receive the new value only.** A second argument, when a component needs one, is a details object `{ reason, event }`, with no `cancel()` ("Nothing cancels the part's handler" above).
- **The reasons a popup opens or closes** (decided on 2026-11-22 with dismissal, #26). Every popup passes `onOpenChange(open, { reason, event })`, where `event` is the key or pointer event that caused the change, or else the browser's own `cancel`, `close` or `beforetoggle`. The reasons are kebab-case strings, typed as `OpenChangeReason` in `floating/dismissal/reason.ts`; later components add to the list and do not rename. A set passes the details through `createControllableSignal`, whose setter takes them as a second argument and hands them to `onChange`.
  - `escape-key`: Escape.
  - `outside-press`: a press outside the popup, on a dialog's backdrop or in a popover's light dismiss.
  - `trigger-press`: the trigger, pressed by pointer or keyboard, or a Context Menu's area by its `contextmenu` event (#100).
  - `close-request`: the browser closed the popup for another reason, such as the back gesture on Android, a `<form method="dialog">` or another popover opening.
  - `trigger-hover`: the pointer rested on the trigger, or left the trigger and the popup (#30). A group closing one popup because another opened reports the other trigger's `pointerenter`.
  - `close-press`: the popup's own close button, pressed by pointer or keyboard, such as Dialog's `Close` (#31).
  - `trigger-focus`: the trigger received keyboard focus, or lost it, such as Tooltip's (#34).
  - `focus-out`: focus moved to an element outside the component, such as out of a Navigation Menu's `<nav>` (#105), or Tab out of a Menu (#99).
  - `link-press`: a link inside the component was activated, by pointer or keyboard, such as a Navigation Menu's `Link` (#105).
  - `item-press`: an item of a menu was activated, by pointer or keyboard, which closes every open menu (#99).
  - `arrow-key`: an arrow key opened or closed a submenu, or a key that moves through a menu closed its open submenu (#99); an arrow key opened or closed a combobox's list (#103).
  - `input-change`: the user typed in a combobox's input, which opened its list (#103).
  - `enter-key`: Enter closed a combobox's list with no item active (#103).
- **Dismissing a popup** (#26; `floating/dismissal/README.md`). A press outside closes on release, as the browser's light dismiss does, and only for a press that also started outside, so a text selection dragged out of the popup keeps it open. Tooltip's Escape calls `preventDefault()`, so a popup below it stays open, and does not stop propagation, so the app's own listeners still see the key. A refused close is opened again once the popup's state has settled, and reported once. Focus leaving closes no popup through dismissal; Tooltip closes on its Trigger's blur itself (#34), and Navigation Menu when focus moves to an element outside its `<nav>` (#105). Navigation Menu's press outside its `<nav>` is its own, the same rule written in a few lines, since `outsidePress.ts` is a dialog's backdrop (#105). Refusing a close needs the controlled form: the details have no `cancel()`.
- **Focus in a popup** (#27; `floating/focus/README.md`). **Initial focus is an `initialFocus` prop**, over the browser's choice, which `autofocus` steers at no cost (`tabindex="-1" autofocus` for a static element at the top of long content). The prop takes an element, or a function called on each opening with the element the browser focused inside the popup, or `null`; it covers what `autofocus` cannot: a lint rule that bans it, focusing the `<dialog>` itself, and an element reached through a ref, which goes in a function (`initialFocus={() => input}`) since refs inside the popup are assigned after its props are read. **Return focus is a `returnFocus` prop**: an element, or a function called when the popup closes with the element the browser focused, or `null` when it found none (`(focused) => focused ?? fallback`); without it the browser returns focus to the element focused before a dialog opened, or to a popover's trigger. A focus the user moved out of the popup while it was shown stays where it is. **Focus returns once the popup has closed**, not when its state turns false: a dialog still shown during an exit animation (#96) is still modal and the page inert.
- **Hover delays** (decided on 2026-11-22 with hover intent, #30; `floating/hover/README.md`). **`delay`** is how long the pointer rests on the trigger before the popup opens, default 600 ms, and **`closeDelay`** how long after it has left the trigger and the popup before it closes, default 0, since the safe area carries it across the gap; both in milliseconds, on the part that takes the popup's state, and a popup may set its own defaults: Navigation Menu's are 300 ms and 200 ms (#105). A delay of 0 opens or closes in the same event. **A touch opens nothing on hover**: compatibility mouse events are not pointer events, so a tap opens nothing either, and Tooltip (#34) has no long press. **A pen opens like a mouse.** **A delay group is a part**, which takes `delay` (for members that set none) and `timeout`, how long after the last closing the next member still opens at once, default 400 ms; it provides the group through context. Tooltip's is `Tooltip.Group` (#34), which renders no element. A component that already holds one value for all its popups needs no group: Navigation Menu's Root works out the delay it passes to `createHover` from its own value, 0 while an Item is open or within `timeout` of the last close (#105). `interestfor` is not used: it is not Baseline (#94).
- **Popups** (decided on 2026-11-22 with Dialog, #31, the first popup; `src/dialog/README.md`). Popover, Tooltip and every Phase 3 popup inherit these.
  - **Parts:** only what a native element cannot do. `Root` holds the open state and renders no element, since a wrapper would sit around the trigger in the page's flow for nothing. `Trigger` is a native `<button type="button">` that opens the popup. `Popup` is the popup element itself, the one in the top layer: a `<dialog>` for Dialog and Alert Dialog, a `popover` element for the rest. `Title` (an `<h2>`) and `Description` (a `<p>`) are parts because the Popup names them. `Close` is a native `<button type="button">` that closes it. **No Backdrop part**: `::backdrop` covers the page behind a modal popup in the top layer, and presence waits for its animations too. The names are in GLOSSARY.md.
  - **The open state** is `open`, `defaultOpen` and `onOpenChange(open, { reason, event })` on the Root. The Trigger reports `trigger-press`, Close `close-press`, and the `floating` layer the rest.
  - **Naming the popup.** The Popup has `aria-labelledby` naming the Title and `aria-describedby` naming the Description, each only while it is rendered: they register their `id` with the Root once mounted (`onSettled`) and take it back on disposal. So a Popup without a Title names nothing, one whose Title is in a `<Show>` follows it, and the server HTML names neither. The consumer's `aria-labelledby` or `aria-describedby` on the Popup wins; they are kept out of the merge, so a wrapper's `undefined` does not remove the Title's ("`undefined` is a value").
  - **The Trigger of a modal popup** has `aria-haspopup="dialog"` and neither `aria-expanded`, which would never be read out as true on a trigger that is inert while the popup is open, nor `aria-controls`, which would name a closed popup that is not shown. The WAI-ARIA modal dialog pattern names none of the three.
  - **The Trigger of a non-modal popup** (decided on 2026-11-22 with Popover, #33) has `aria-haspopup="dialog"`, `aria-expanded` (`"true"` or `"false"` by the state, since the Trigger stays in the page while the popup is open), and `aria-controls` and `popovertarget` naming the Popup, which is always in the document. `popovertarget` makes the browser count a press on the Trigger as one on the popover, so light dismiss leaves it open; the Trigger's click opens and closes it through the state and calls `preventDefault()`, so the browser does not toggle it as well, and the popover is shown in the flush that places it. The Popup has the `dialog` role without `aria-modal`. There is no WAI-ARIA popover pattern; `src/popover/README.md` has the reasons.
  - **A Popup must be the element the browser opens:** Dialog's `render` must return a `<dialog>`, and a development build warns otherwise, as for a part that must be a button. Its props have no `tabindex`, as Solid's `<dialog>` type has none.
  - **Focus props are on the Popup:** `initialFocus` and `returnFocus` ("Focus in a popup" above). A controlled popup with no Trigger, opened from the app's own button, returns focus to that button, as the browser does; `returnFocus` covers a button that is gone.
  - **Modal or not is a component, not a flag.** Dialog is always modal; a non-modal popup is Popover's (section 6, rule 6).
  - **Server HTML of a popup open by default** renders it closed, and hydration opens it. A `<dialog open>` would be non-modal, laid out in the page's flow over a page that stays usable, and a closed popover is `display: none` anyway. The `data-*` attributes follow the state, so the closed Popup already has `data-open`.
  - **A closed Popup stays in the document**, `display: none` (#96), so its content keeps its state between openings.
  - **A popup that builds on another** re-exports its parts and shares its Popup's code, as Alert Dialog does Dialog's (#32; section 6, rule 4). Alert Dialog differs only where the WAI-ARIA alert dialog pattern does: the `alertdialog` role on the `<dialog>`, and no outside press, so its entry bundles none. Escape closes it, as the pattern's keyboard is the modal dialog's, and initial focus is the browser's, which the consumer steers to the least destructive action by order, `autofocus` or `initialFocus`; no part marks the cancel action. A shared part's development messages name both components where it cannot tell them apart. `src/alert-dialog/README.md` has the details.
  - **Not built:** a Trigger outside its Root, several Triggers for one popup, an imperative handle, a drawer swiped away. Each is in `src/dialog/README.md`, "Left out", with the reason.
- **`data-*` attributes** are `""` when they apply and absent otherwise: `data-checked`/`data-unchecked`, or `data-indeterminate` instead of either while a Checkbox is partly checked, so exactly one of the three applies (#18), `data-pressed`/`data-unpressed` on a Toggle and a Toggle Group's items (#16, #17), `data-horizontal`/`data-vertical` on a part with an orientation, beside `aria-orientation` where the role takes one (#19), `data-indeterminate`/`data-progressing`/`data-complete` on every part of a Progress, where indeterminate means the value is unknown, not partly checked (#20), `data-open`/`data-closed` on every part of a Collapsible (#22) and of an Accordion's Item (#23), on a popup (#96), and on a Navigation Menu's Item, Trigger and Panel (#105), `data-selected`/`data-unselected` on a Tabs' tabs and Panels (#24), `data-active` on the active item of a list (#97), `data-disabled`, `data-readonly`, `data-required`, on every part of the component, but a Checkbox Group's and a Radio's `data-required`, which is on its Root only, since the group is required and no box or radio is (#146, #147). `data-invalid` while a field shows an error and `data-touched` once it was touched, on every part of a Field (#141); `data-valid`, `data-dirty`, `data-filled` and `data-focused` are left out ("Fields" below). No `data-focus-visible`: `:focus-visible` matches the button. No further attribute marks a popup's entry or exit: `data-closed` while it is still shown is the exit, since a closed popup at rest is `display: none`, and its entry is the consumer's `@starting-style` or `@keyframes` on `[data-open]` (#96).
- **A group of items is one tab stop** (roving tabindex), as the WAI-ARIA keyboard interface practice prescribes for composite widgets: the item that last had focus, else the first enabled one, has `tabindex="0"` and arrow keys move focus. Items register with the group once mounted, so the order follows the document; the server HTML gives the first enabled item the tab stop. Worked out on Toggle Group (#17). `core/rovingFocus.ts` holds it since Tabs (#24), where the tab stop is the selected tab instead, as the tabs pattern says, and disabled tabs stay focusable, as the keyboard interface practice says of tabs. In a Radio the tab stop is the checked radio, else the first enabled one, and an arrow key checks the radio it moves to (#147).
- **The active item of a list** (decided on 2026-11-23 with list navigation, #97; `floating/list-navigation/README.md`) is the item the keyboard acts on, in a list popup: focused in Menu, named in `aria-activedescendant` in Select and Combobox. It carries `data-active`, so one style works in both, since an item named in `aria-activedescendant` never has focus. Unlike a group's tab stop, it does not last: no item is active while the popup is closed or in the server HTML, and the component sets one on each opening, such as the first or last by the key that opened it. The component says which items the keys reach (disabled menu items and options stay reachable, as the keyboard interface practice says) and does the activating. Wrapping is off unless the component turns it on. The pointer moving on an item makes it active without scrolling; a key scrolls it into view at the near edge. An item named in `aria-activedescendant` takes `props.id ?? createUniqueId()` and registers it once mounted, as a popup's Title does.
- **Typeahead** (decided on 2026-11-23 with typeahead, #98; `floating/typeahead/README.md`). In Menu, Select and the popups built on them, printable characters move to the next item whose text starts with what was typed, case and accents ignored. The typed string resets 1 second after the last key, what Chromium's native `<select>` waits, and is not a prop. The same character repeated cycles through the items that start with it. Space while a string is being typed joins it: the handler reports the key used, and the part skips its Space activation, with no `defaultPrevented` check ("Nothing cancels the part's handler"). It searches the items the keys reach, so disabled items match where list navigation moves to them. An item's text is its text content, read when a key is typed, or the `text` its part registers with list navigation when its content is not its label, which a Select's Value part reads too. A printable character on a closed Select opens it and moves to the first match without changing the value, as the select-only combobox example does: the component opens it, and the typed string goes on. Typeahead renders no part, generates no id, sets no `data-*` attribute and adds no open-change reason.
- **A value along a range reaches CSS as a custom property**, the percentage of the range, which the root sets and every element inside it inherits: `--progress` on a Progress, such as `25%` (#20), `--meter` on a Meter (#21), and `--slider` on a Slider (#148). The part draws nothing, and the consumer sizes an indicator with it (`width`, `scale` or an inset), so a vertical or right-to-left bar needs no prop. An indicator is a part only when it carries state: Progress.Indicator has its `data-*` attributes, while a Meter, with none, takes a plain element. The value's text is formatted with `Intl.NumberFormat`, taking its options as `format` and a `locale`; a Slider's `format` also takes a function, `(value) => text`, for text that is not a number (#148).
- **Boolean props are camelCase**, `readOnly`, because they are component props, not attributes.
- **`id` goes on the labelable element**, the button, which takes the consumer's `id`.
- **Generated ids belong to the root.** When one part names another part rendered after it, as a Collapsible's Trigger names its Panel in `aria-controls`, the root generates the id with Solid's `createUniqueId`, which the server render and hydration agree on, and shares it through context. The part that carries the id takes no `id` from the consumer (it is left out of its props type and of the merge): the server renders parts in document order, so a later part's own `id` could not reach an earlier part that names it, and the server HTML would link to nothing. A consumer who needs an anchor puts an `id` on an element inside the part. A part that links only its own elements, or is named by a part rendered after it, keeps `props.id ?? generated` ("`undefined` is a value" above). Decided on Collapsible (#22), the first component that links its own parts; revisit at Tabs, Dialog or Field if a case does not fit. Dialog (#31) revisited it for a part named by its parent: a Popup names its Title and Description, rendered inside it, only once they are mounted, so its server HTML names neither, and each keeps `props.id ?? generated` and hands it over then ("Popups" below). In a component of repeated sections, the part that holds a section is its root: an Accordion's Item generates its Panel's and Trigger's ids, and the Trigger, which keeps `props.id ?? generated` since the Panel names it in `aria-labelledby`, hands its `id` to the Panel through the Item's context (#23). Where the linked parts sit in different containers, as a tab in the List and its Panel beside it, nothing holds both: Tabs' Root generates one id and derives each tab's and Panel's from the shared `value`, and a tab with the consumer's `id` hands it to its Panel through the Root's context, keyed by `value` (#24).
- **The hidden input is the form's view of the control.** It is always rendered and takes `name`, `value`, `form`, `required` and `disabled`. A change goes through it (the button clicks it), so the form sees a checkbox's native `input` and `change` events; its click is stopped before it bubbles, so ancestors see the user's click once. A form reset goes back to the default value, through the setter, so a controlled part asks. When the browser blocks a submission and focuses the input, focus moves to the button. `core/hiddenInput.tsx` holds it since Radio (#147), for Switch, Checkbox and a Radio's Items.
- **A part used outside its root throws** a descriptive error in development builds (`isDev`).
- **No state argument** for `render` or `children` yet (see "Polymorphism"), but for a Select's Value and a Combobox's Status, which show text only the app can write; the `data-*` and `aria-*` attributes carry the state.
- **Positioned popups** (Popover, Tooltip, the list popups; decided on 2026-11-22 with positioning, #25, and confirmed by Popover, #33). `floating/positioning/README.md` and `src/popover/README.md` have the details.
  - **Parts** (#33): a positioned popup has the parts of a popup ("Popups" above), plus an **Arrow**, a part because the Popup places it and because an app that renders none does not bundle the `arrow` middleware: the Arrow hands its middleware to the Popup once mounted. It is `aria-hidden`, carries the Popup's `data-side` and `data-align`, and the consumer's CSS puts it on the Popup's edge. **No positioner part**: the Popup is the element positioned (below). **No Anchor part**: the Popup takes an `anchor` prop, an element, a virtual element or a function returning one (`anchor={() => field}` for a ref), and is placed against the Trigger without it.
  - **Middleware:** `offset`, `flip` and `shift` always, `arrow` with an Arrow. Popover ships neither `size` nor `hide`: no part carries them, and a prop that turned them on would be a flag (section 6, rule 6). Add them with the popup that needs them, such as a list popup that scrolls.
  - **Placement props:** `side` (`"top"`, `"right"`, `"bottom"` or `"left"`) and `align` (`"start"`, `"center"` or `"end"`), not one `placement` string: each is one word, a consumer changes one without restating the other, and they are the values of `data-side` and `data-align`. Sides are physical; `start` and `end` follow the writing direction. `sideOffset` is the gap from the anchor and `alignOffset` the shift along it, in pixels; `collisionPadding` is the space kept from the viewport's edges. Defaults are the popup's own.
  - **The positioned element is the popup itself,** the `popover` element in the top layer (#94), not a wrapper around it: the top-layer element is the one whose box is placed, and a wrapper would be one more part in every popup.
  - **Written as `top` and `left`,** through `inset: <y>px auto auto <x>px`, rounded to device pixels, with the strategy `fixed`. Not `translate`, so that `transform`, `translate` and `scale` stay free for the consumer's entry and exit animations. A popup is placed before it is painted: it is shown first, and the placement lands in the same task.
  - **`data-*` attributes** on the popup: `data-side` and `data-align`, with the resolved values (after a flip), and, from a popup that passes `hide`, `data-anchor-hidden`, `""` while the anchor is scrolled out of view.
  - **CSS variables** on the popup, short and unprefixed like `--progress` and `--meter`, since they are set on the popup and inherited only inside it: `--anchor-width` and `--anchor-height`, `--available-width` and `--available-height` from a popup that passes `size` (the space left in the viewport, for `max-width` and `max-height`), and `--transform-origin` (the point nearest the anchor, for `transform-origin`).
- **Popups that open on hover and focus** (decided on 2026-11-22 with Tooltip, #34; `src/tooltip/README.md`). Preview Card revisits them. Navigation Menu revisited them (#105): it opens on hover and on a press, not on focus, since a disclosure opens on a press ("Site navigation" below).
  - **Parts:** a positioned popup's, without the Title, Description and Close a tooltip has no use for, plus the delay group's part, `Tooltip.Group`, which renders no element and is bundled only by an app that renders it. The hover delays (`delay`, `closeDelay`) are on the Root.
  - **Opening:** on hover after the delay (`trigger-hover`), and at once on keyboard focus, which is focus that matches `:focus-visible` (`trigger-focus`). A press that focuses the trigger opens nothing, nor does a touch.
  - **Closing:** on Escape (`floating/dismissal/escape.ts`), on blur (`trigger-focus`), when the pointer leaves the trigger and the popup (`trigger-hover`), and when the trigger is pressed (`trigger-press`), by pointer or keyboard, since the press opens what the tooltip would cover; a press before the delay has ended cancels the opening until the pointer leaves and comes back. Scrolling closes nothing of its own.
  - **Hovered or focused keeps it open** (WCAG 1.4.13): the close from hover is ignored while the trigger has keyboard focus, and the close on blur while the pointer is on the trigger or the popup (`:hover`).
  - **The description link:** the Trigger always names the Popup in `aria-describedby`, since a closed Popup stays in the document and an element referenced directly gives its text even when hidden. The consumer's `aria-describedby` wins; `false` removes it.
  - **No focus in the popup**, and no interactive content: that is a Popover. **A disabled trigger opens nothing**, since it cannot be focused; `aria-disabled="true"` is the way round. The popup is `popover="manual"` and `side` defaults to `"top"`.
  - **The Trigger may render any element that takes focus**, such as a link, and no warning is given for one that is not a `<button>`, unlike the Trigger of "Popups" above: a tooltip needs only focus and pointer events, not a button's press.
- **List popups** (decided on 2026-11-23 with Menu, #99, the first list popup; `src/menu/README.md`). Context Menu and Menubar inherit these, and Select all but where focus goes ("Selects" below).
  - **Parts:** a positioned popup's Root, Trigger and Popup, then what a native element cannot do in a list: an `Item` for each role (Menu's `Item`, `CheckboxItem`, `RadioItem`), a group that holds a value (`RadioGroup`), a `Group` named by its `GroupLabel` (registered once mounted, as a Title is), an `ItemIndicator` that carries a checked item's `data-checked` or `data-unchecked`, always rendered and `aria-hidden`, as Checkbox's Indicator. No Title, Description or Close: the Popup is labelled by its trigger in `aria-labelledby`, which keeps `props.id ?? generated`, and closes when an item is activated. No Separator part: a native `<hr>` is a separator inside a `menu`. No Arrow until asked.
  - **Non-modal, `popover="auto"`**, with the list's role on the Popup: the browser dismisses it on Escape and a press outside, and nests a submenu's Popup, rendered inside its parent's. The Trigger has `aria-haspopup` with the list's role, `aria-expanded`, `aria-controls` and `popovertarget`, and opens through the state as Popover's does.
  - **Focus goes to the first item whenever the list opens**, by a press, a key, `defaultOpen` or a controlled `open`; Up Arrow on the Trigger starts at the last. List navigation's roving form, wrapping, with typeahead in the open list; an item whose content is not its label takes a `label`.
  - **Items:** `disabled` gives `aria-disabled` and `data-disabled`, keeps the item reachable, and calls no `onClick`; a disabled link's click is cancelled. A click, Enter or Space activates an item, calls its `onClick`, and closes every open list (`item-press`), the key event as the details' `event`; a link rendered with `render` follows itself on Enter. A checkbox or radio item changes on a click and Enter, and closes; on Space it changes and stays open, as the menu pattern's optional Space. Checked state is `checked`/`defaultChecked`/`onCheckedChange` on a checkbox item and `value`/`defaultValue`/`onValueChange` on a radio group, `null` for none.
  - **Submenus:** `Submenu` holds a submenu's state as a Root does and renders no element; `SubmenuTrigger` is an item of the menu around it, and the submenu's `Popup` the sibling right after it, as the menu pattern places it. Right Arrow (Left right to left), Enter and Space open it with focus on its first item; Left Arrow closes it and focuses its trigger at once (`arrow-key`); a key that moves through the parent, Up, Down, Home, End or a typed character, closes it. The pointer resting on the trigger opens it after `delay` (default 100 ms) and leaving the trigger and the submenu closes it across the safe area (`trigger-hover`): only a pointer that moves counts, so a list opened by the keyboard under a still pointer opens no submenu, and Menu uses `hover/safeArea.ts` alone, not `createHover`. Placed at the inline end, aligned to the start.
  - **Closing:** Escape closes the list that has focus and returns focus to its trigger; focus returns to a submenu's trigger, which the browser does not do for a nested popover. Tab and Shift+Tab out of the list that has focus close every list (`focus-out`), and focus goes where the key sent it, or to the Trigger from a submenu's trigger; no other focus leaving closes it. `data-open` and `data-closed` are on the Trigger and the Popup, and on a submenu's trigger.
  - **Placement** as Popover's, with `side` `"bottom"` and `align` `"start"` by default, and a `returnFocus` prop; no `initialFocus`, since focus goes to an item.
- **Context menus** (decided on 2026-11-23 with Context Menu, #100; `src/context-menu/README.md`). A list popup opened from an area instead of a button; there is no WAI-ARIA context menu pattern, so the menu pattern decides the menu, and these decide the opening.
  - **One listener:** the area's `contextmenu` event, which browsers fire for a secondary-button press, Ctrl+click on macOS, Shift+F10, the Menu key and, on Android, a long press. The Trigger cancels it and opens the menu (`trigger-press`), with focus on the first item. iOS Safari fires none on a long press, and no long-press timer is written: an app keeps the actions reachable another way, such as a Menu button.
  - **Placement:** at the pointer for a press, the top-left corner there, flipped and shifted into view; below the focused element for a key, which Chromium sends with `button` `-1` and `pointerType` `"mouse"` (the Pointer Events spec: `pointerType` `""`; a long press has `"touch"`). Before the first `contextmenu`, a `defaultOpen` or controlled menu is placed below the area.
  - **The area is not a button:** a `<div>` with no role, no `aria-haspopup`, `aria-expanded`, `aria-controls` or `tabindex`, and `data-open`, `data-closed` and `data-disabled`. The Popup is labelled by nothing; the consumer gives `aria-label`. `disabled` cancels nothing, so the browser's own menu shows.
  - **A second `contextmenu` while open moves the menu**, closes its submenus and focuses the first item, with no close and reopen: Chromium's light dismiss ignores a secondary-button press. One inside the menu, a right-click on an item or the Menu key with focus on one, is cancelled by the Popup, so the browser's menu does not show over it.
  - **Focus returns to the element the menu opened from**, which the Trigger hands to Menu's state as its trigger: the browser returns focus from the first popover of a stack only, so after an item in a submenu Menu does it.
- **Menubars** (decided on 2026-11-23 with Menubar, #101; `src/menubar/README.md`). A row of list popups, the WAI-ARIA menubar pattern; each menu is Menu's, so "List popups" above holds for it. A menubar is for an application's commands; site navigation is Navigation Menu's (below).
  - **Parts:** `Root` renders the bar, a `<div role="menubar">` named by `aria-label` or `aria-labelledby`, as Navigation Menu's Root renders its `<nav>`. `Menu` is one menu's state, Menu's Root, which renders no element: each menu has its own `open`, `defaultOpen` and `onOpenChange`. `Trigger` is Menu's Trigger with the `menuitem` role, a native `<button type="button">`, so Enter and Space click it and light dismiss counts a press on it through `popovertarget`. The Popup and everything in it are Menu's parts.
  - **One tab stop:** the item of the bar that last had focus, else the first, which the server HTML gives the tab stop, as Toggle Group does. Right and Left move along the bar, wrapping, mirrored right to left, with Home, End and typeahead: list navigation's roving form, horizontal, whose active item lasts while the bar does, without `data-active`. No vertical bar: its keys clash with its menus', and Menu's Trigger would need a flag.
  - **Opening:** a press, Down, Enter and Space open a menu with focus on its first item, Up on its last; Enter and Space on an item whose menu is open move focus into it. Once one menu is open, moving to another item, by Right, Left, Home, End or a character on the bar, or Right and Left inside a menu (Right on an item with no submenu, Left in a menu of the bar), closes it and opens that item's menu with focus left on the item, as the pattern recommends (`arrow-key`). The pointer moving onto another item while a menu is open does the same (`trigger-hover`); while none is open, hover opens nothing, so the bar needs no hover delay or group. A press on the item hover just opened keeps its menu open.
  - **Closing:** Escape closes the menu that has focus, and focus returns to its item in the bar; Tab and Shift+Tab close every menu and leave the bar, Shift+Tab by moving focus to the item first.
- **Selects** (decided on 2026-11-23 with Select, #102; `src/select/README.md`). A list popup that holds a value and is a form control: the WAI-ARIA select-only combobox example for the Trigger and the listbox pattern for the list. Combobox revisits them.
  - **Built, not a styled native `<select>`:** `appearance: base-select` was not Baseline on 2026-11-23 (`web-features` 3.47.0: Chrome and Edge 135, Safari 27, no Firefox), and no exception is made for it, since without it a browser shows its own picker ("What the browser does for popups" below). Check again once Firefox ships it.
  - **Parts:** a list popup's `Root`, `Trigger`, `Popup`, `Item`, `ItemIndicator`, `Group` and `GroupLabel`, and a `Value`. The Popup is the `listbox`; there is no separate list part, no Portal, and no part for an icon or an item's text.
  - **Focus stays on the Trigger**, a native `<button type="button" role="combobox">` with `aria-haspopup="listbox"`, `aria-expanded`, `aria-controls`, `popovertarget` and, while an item is active, `aria-activedescendant`: list navigation's `aria-activedescendant` form, not the roving one. One element takes every key, closed and open, so typing on a closed Select is the same handler; nothing returns focus, and the Popup cancels its `mousedown` so that a press in the list moves none. A combobox takes no name from its content: its content is its value, and a `<label>` names it.
  - **Keys:** as the example. Closed, Down Arrow, Alt+Down Arrow, Enter and Space open the list on the selected item, else the first; Up Arrow and Home on the first, End on the last; a printable character on its match. Open, Down and Up move without wrapping, with Home, End, and PageUp and PageDown by ten; Enter, Space and Alt+Up Arrow select the active item and close; Tab selects it, closes (`focus-out`) and lets focus move on; Escape keeps the value. Selection does not follow the active item. Opening by any key reports `trigger-press`, and a selection `item-press`. The item a list opens on, the selected one, else the first, is derived from the open state and the value, not written to the list by an effect, so the Trigger runs once per opening.
  - **The value** is `value`, `defaultValue` and `onValueChange` on the Root: an item's `value`, a string, `null` for none. Several selected items are left out: they are another keyboard model, a list that stays open and a value of another type, an array (`core/listValue.ts`), so not a flag (section 6, rule 6).
  - **Items** are `<div role="option">` with `aria-selected`, `data-selected` or `data-unselected`, which the `ItemIndicator` carries, and an `id` the Trigger names in `aria-activedescendant`: the consumer's, else a generated one, `props.id || generated`, since `id={false}` must not leave the active item unnamed. A disabled item stays reachable and is not selected.
  - **The Value knows the label from the item**, once mounted: the selected item's `label`, else its text content without what is `aria-hidden`, such as the ItemIndicator's check mark, which typeahead matches too. The items are rendered after the Value, so the server HTML, and hydration's first render, show the value itself; a Select whose labels differ from its values gives the Value a function as its children, `(value) => label`, which the server calls too. It and a Combobox's Status, whose function gets the number of items ("Comboboxes" below), are the two parts whose `children` is a function ("No state argument" above still holds for every other).
  - **The form's view is a visually hidden `<input>`** right after the Trigger, which takes `name`, `form`, `required`, `disabled` and `autocomplete` from the Root ("The hidden input is the form's view of the control" above). Not `type="hidden"`, which is left out of validation and autofill, and not a native `<select>`, which needs an `<option>` per item in the server HTML. A selection sets the input and fires `input` and `change`, and the Select takes its value from the `change`, so a value the browser fills in takes the same path: it selects the item with that `value`, else the one with that label. A reset goes back to `defaultValue` through the setter.
  - **Sizes are the consumer's CSS:** `min-width: var(--anchor-width)` makes the Popup as wide as the Trigger, and the Popup always passes `size`, so `max-height: var(--available-height)` with `overflow-y: auto` keeps a long list in the viewport ("Positioned popups" above).
- **Comboboxes** (decided on 2026-11-23 with Combobox, #103; `src/combobox/README.md`). An input that picks one value out of a list: the WAI-ARIA combobox pattern as its list autocomplete example applies it, with manual selection. A form control, as a Select is ("Selects" above), whose parts it repeats where they are the same; it builds on no popup. Autocomplete builds on it ("Autocompletes" below).
  - **Parts:** a Select's `Root`, `Popup`, `Item`, `ItemIndicator`, `Group` and `GroupLabel`, and an `Input`, the combobox itself; a `Trigger` and a `Clear`, native buttons with `tabindex="-1"` whose presses leave focus in the input; a `List`, the `listbox`, inside the Popup, since a message for an empty list and a `<Loading>` fallback go beside it and a `listbox` holds only options and groups; and a `Status`, a `<div role="status">` whose children are a function of the number of items, `(count) => …`, shown while the list is open, for an empty list and for a screen reader. Menhir writes no text, since it does not know the app's language. No Value: the input shows the selected item's label.
  - **A manual popover**, not `auto`: the input cannot be a popover's invoker, since `popovertarget` exists only on buttons, so a press in it to move the caret would light-dismiss the list. Closing is the Combobox's: Escape on the input, and focus leaving it, which a press outside does; focus lost to another window closes nothing. It bundles no dismissal.
  - **Two values:** `value`, `defaultValue` and `onValueChange`, the selected item's `value` or `null`, which the form receives through a hidden input; and the input value, the text, `inputValue`, `defaultInputValue` and `onInputValueChange(text, { reason, event })`, with the reasons `input-change`, `item-press`, `escape-key`, `clear-press`, `focus-out` and `reset`. Selecting an item puts its label in the input; focus leaving puts the selected item's label back, or clears the value when the user emptied the text. Until the user types, an uncontrolled Combobox without `defaultInputValue` shows the selected item's label once the items have mounted, so the server HTML shows `defaultInputValue`, as Select's Value shows its function's label.
  - **Filtering is the consumer's:** it renders the items that match, and items that leave the list leave list navigation. `includesText(text, query)`, a separate import from `menhir/combobox`, is the filter for the usual case, with `Intl.Collator` (section 6, rules 5 and 6). A consumer filters by the text for `input-change` only, so a list opened after a selection shows every item.
  - **Items that load** come from `createDeferred(() => search(query()))` under `<Loading>`; the Combobox writes its text and open state in `onFlush`, so a search the text starts holds neither, and the input binds its `value` to a draft written on each edit, since a binding that re-runs in the edit's flush would write the old text over it (Solid's `UNCOMMITTED_INPUT_OVERWRITTEN`). The Status calls its function while closed too, so a read of pending data starts at mount, where `<Loading>` shows its fallback, and opening is not held until the data lands.
  - **Keys** as the example: typing opens the list with no item active; Down and Up open it on the first or last item and move, wrapping, since Home, End, Left and Right belong to the text; Alt+Down opens and Alt+Up closes; Enter selects the active item and is cancelled, or with none active closes the list and lets a form submit; Escape closes the list, and on a closed one empties the text and the value, cancelled only when it did something, so a dialog around an empty Combobox closes; Tab selects nothing. A key down while an input method composes is the method's. Focus alone opens nothing, nor does a press in the input.
- **Autocompletes** (decided on 2026-11-23 with Autocomplete, #104; `src/autocomplete/README.md`). A Combobox picks a value from a list; an Autocomplete is free text with suggestions: the same WAI-ARIA list autocomplete example, whose typed text "becomes the value of the combobox" unless the user picks a suggestion. It builds on Combobox ("Comboboxes" above), as Alert Dialog builds on Dialog, and keeps its decisions but where the value differs.
  - **Built on Combobox, not a flag on it.** The difference is the value, not one prop: as a flag it would change the form's view, focus leaving, the items and the ItemIndicator, and every Combobox would ship both (section 6, rule 6). `popupBases` names `autocomplete: "combobox"`. Its own `Root`, `Input` and `Item`; Combobox's `Trigger`, `Clear`, `Popup`, `List`, `Group`, `GroupLabel`, `Status` and `includesText`, re-exported. Its Root shares a combobox through Combobox's context, typed as `ComboboxBase`, so those parts work inside it unchanged, and both Roots, Inputs and Items call Combobox's `createComboboxBase`, `createComboboxInput` and `createComboboxItem`. In development, a shared part outside either Root throws an error naming both components, and each component's own Input and Item throw inside the other's Root. An app with both pays 233 B over Combobox alone.
  - **The value is the text:** `value`, `defaultValue` (`""`) and `onValueChange(text, { reason, event })`, with Combobox's input-value reasons but `focus-out`. No `inputValue`.
  - **The Input is the form's control**, taking `name`, `form`, `required` and `disabled`: the browser validates and focuses it, and no hidden input is rendered. A form reset goes back to `defaultValue` through the setter.
  - **Accepting a suggestion** (a click, or Enter on the active one) puts its `value` in the input and closes the list; text that matches no suggestion is kept, and focus leaving keeps it too. Escape on a closed list empties the text.
  - **No selected item:** an item has `aria-selected="true"` only while it is the active item, as the example does, and no `data-selected` or ItemIndicator.
  - **List autocomplete only** (`aria-autocomplete="list"`): inline completion (`both`) is left out, since managing the caret on every key would ship in every Autocomplete.
- **Site navigation** (decided on 2026-11-23 with Navigation Menu, #105; `src/navigation-menu/README.md`). The WAI-ARIA disclosure pattern as its navigation example applies it, with hover added. Not a menu: WAI-ARIA's guidance is that site navigation uses disclosure buttons and links, not `menu` roles, so it does not build on Menu.
  - **A Root that renders an element.** Its Root renders a `<nav>`, unlike a popup's Root, which renders nothing: the `<nav>` is the landmark, and the boundary that focus leaving and a press outside are measured against.
  - **Panels, not Popups.** Its content part is a `Panel`, a `<div>` in the page's flow, `hidden` while closed, as Collapsible's is, and placed by the consumer's CSS ("What the browser does for popups" below). Closed content stays in the document, so the links are in the server HTML, and a `defaultValue` Panel is rendered open by the server, since nothing needs the top layer. The exit animation is the consumer's CSS (`transition-behavior: allow-discrete`).
  - **Parts:** `Root` (`<nav>`), `Item` (`<li>`, which holds the entry's `value` and generates its Panel's `id`, as an Accordion Item does), `Trigger` (a native `<button type="button">` with `aria-expanded` and `aria-controls`, and no `aria-haspopup`), `Panel` (takes no `id`) and `Link` (an `<a>` that closes the menu, `link-press`). No List part, no Title, Description or Close.
  - **The state** is `value`, `defaultValue` and `onValueChange(value, { reason, event })` on the Root: the open Item's value, `null` when none is open, one at a time.
  - **Opening:** on a press (`trigger-press`) and on hover (`trigger-hover`), always, with no flag (section 6, rule 6); not on focus. The press-only form is a recipe on Collapsible, on the docs page. While an Item is open, or within `timeout` of the last close, hovering the next opens it at once and closes the open one in one change. A Panel opened by a press stays open when the pointer leaves; a press on the Trigger of a Panel hover opened closes it.
  - **Closing:** Escape (`floating/dismissal/escape.ts`), which returns focus to the Trigger if focus was inside the Item; focus moving to an element outside the `<nav>` (`focus-out`; focus lost to nothing, such as the window's, does not close); a press outside the `<nav>` (`outside-press`), on release and only for a press that also started outside; a Link (`link-press`).
- **Fields** (decided on 2026-11-23 with Field, #141, the first form component; `src/field/README.md`). Input, Form, Fieldset, Checkbox Group, Slider, Radio and Number Field inherit these. No WAI-ARIA pattern covers a field; the practice on names and descriptions, WCAG 3.3.1 and 3.3.2 and the HTML standard on constraint validation do.
  - **Parts:** `Root` (a `<div>`), `Label` (a `<label for>` the control), `Control` (an `<input>`), `Description` (a `<p>`) and `Error` (a `<p>`, rendered only while the field shows an error). Label is a part because it is rendered before the control it names: the Root generates the control's `id`, so the server HTML is labelled ("Generated ids belong to the root"); `for`, not `aria-labelledby`, since every control is labelable.
  - **A control joins a Field as `Field.Control`'s `render`:** `render={(p) => <textarea {...p} />}`, `render={(p) => <Input.Root {...p} />}`, `render={Switch.Root}`, `render={Checkbox.Root}`, or `render={Select.Trigger}` inside `Select.Root`, which keeps its own `name`, `required` and `disabled`. The control gets the field's `id`, `name`, `disabled`, `aria-describedby`, `aria-invalid` and `data-*` attributes, and its children go through; a control's value props (`checked`, `onCheckedChange`) go on it inside a `render` function, since `Field.Control` is typed for an `<input>`, which has no `onCheckedChange`. The Field's `data-*` attributes stay on the control's element: a Switch's Thumb and a Checkbox's Indicator carry only the control's state, and CSS reaches them through the button around them, `[data-invalid] .thumb` (decided on 2026-11-23 with #143). No control reads a context of Field's, so a control outside a Field pays nothing: `test/bundle-size/fieldModules.test.ts` checks that `menhir/switch`, `menhir/checkbox`, `menhir/checkbox-group`, `menhir/radio`, `menhir/input`, `menhir/number-field` and `menhir/slider` bundle no module of `src/field`.
  - **Validity is read from every control inside the Root**, on each `input`, `change`, `focusout` and `invalid` (in the capture phase): the first `input`, `select` or `textarea` the browser validates and finds invalid is the field's, so the hidden input of a Switch, a Checkbox or a Select counts. The field is invalid when the browser says so, or the app passes `invalid` or an `error` message from outside, which is shown over the browser's `validationMessage`. Errors from outside work without the browser's validation, and do not block a submission: Field calls no `setCustomValidity()`. No `validate` prop: a memo, or an async memo with `isPending`, is Solid's, and its result goes in as `error`.
  - **Field holds no value,** so it tracks no dirty state: the value stays in the control or in the app, each control has its own type of value, and holding it would make Field a form-state library.
  - **Field tracks touched:** once focus has left the Root, to an element outside it or to none; once a control in it fired `change`; once a submission of its form was attempted (its `submit` event, or an `invalid` event in it), which touches every Field of the form. A form reset clears it. **The error shows once the field is touched**, then follows each change. The app writes no touched state.
  - **ARIA:** `aria-describedby` names the Description, from the server HTML on, and the Error while it is rendered (registered once mounted, as a popup's Title is); the consumer's wins. `aria-invalid="true"` while the error shows. Not `aria-errormessage`, which several screen readers read while the field is valid (a11ysupport.io, 2023 to 2025). The Error is not a live region.
  - **The browser's bubble is kept:** canceling `invalid` would also stop the browser focusing the first invalid control, so hiding it is Form's (#144), with `novalidate`.
  - **Field's own state is written in `onFlush`,** as an uncontrolled part's is.
- **Inputs** (decided on 2026-11-23 with Input, #142; `src/input/README.md`). A text control whose value can be controlled, beside `Field.Control`, which renders a native `<input>` with no value API.
  - **An entry point of its own, not a recipe on `Field.Control`.** Solid writes `value={text()}` only when `text()` changes, so with `onInput` alone a declined edit stays on screen, a form reset sets the element back to its `value` attribute (`""`, or the server's first text after hydration) with no `input` event and parts it from the app's state, and a write while an input method composes would end the composition. Input covers the three in 175 B over Separator, which is all `core` (921 B in all), not as a flag on `Field.Control`, which every Field would pay for.
  - **The value is a string:** `value`, `defaultValue` and `onValueChange(value, { reason, event })`, with `input-change` and `reset`. The empty text is `""`, not `null`; `undefined` means uncontrolled, and a wrapper's `value={undefined}` leaves the `value` key out of the element's props, since Solid writes `""` for it. Native `onInput` and `onChange` run as written.
  - **Uncontrolled is native:** the text lives in the element, `defaultValue` is Solid's binding of the `value` attribute, and Input holds no signal. **Controlled holds:** after each edit's flush the element is put back to `value` when the two differ, never while an input method composes (`isComposing`), and again on `compositionend`. **A form reset asks:** a controlled Input keeps its text through the browser's reset by making it its `value` attribute during the `reset` event; then, in a task (a real press runs microtasks between the listeners, before the controls are reset), an Input whose text is not `defaultValue` calls `onValueChange(defaultValue, { reason: "reset" })`, unless the app cancelled the reset: the reset is the default action, so `defaultPrevented` is the app declining it.
  - **A textarea through `render`**, as on `Field.Control`. **It joins a Field as `Field.Control`'s `render`**, with the value props on `Input.Root` inside the function, and imports only `core`: `test/bundle-size/fieldModules.test.ts` checks that `menhir/input` bundles no module of `src/field`.
  - **Text types only:** `number` is Number Field (#149), `range` Slider (#148), `checkbox` Checkbox, `radio` Radio (#147); `file` cannot be controlled. A one-time code is a docs recipe, one input with `autocomplete="one-time-code"`; a box per character is left out. No `data-*` attributes of its own: the native pseudo-classes match, and a Field adds its own.
- **Forms** (decided on 2026-11-23 with Form, #144; `src/form/README.md`). A `<form>` that hands errors to its Fields and blocks a submission while a control is invalid. The HTML standard on form submission and constraint validation, and the Solid 2.0 forms guide (docs.solidjs.com/guides/forms, where v2.solidjs.com redirects), decide it.
  - **Not a form-state library:** Form holds no values, dirty or touched state. Values stay in the controls, read with `FormData` as in the Solid 2.0 forms guide, or in the app's own store, where nested and array values are plain data. The docs guide "Forms without a library" (`website/src/routes/docs/forms.tsx`) builds the app the order of Phase 4 was set against: a store with a nested value and an array of rows, a schema run on submit, an error that depends on another field shown once touched, a pending submit button and reset, and the uncontrolled form with the router's form action.
  - **One part, exported as itself:** `import { Form } from "menhir/form"`, no namespace.
  - **Errors reach each Field through a context in `core`** (decided with the maintainer): Form provides `core/formContext.ts`, and `Field.Root` reads the error under its `name`. Form imports no module of Field, nor Field of Form (`test/bundle-size/fieldModules.test.ts`); each Field pays the read, 33 B, inside or outside a Form. The alternative, `error={errors().email}` on each Field, costs nothing but leaves to every app showing the errors in the server HTML after a submission made before hydration, and hiding a stale one.
  - **`errors` is keyed by the Field's `name`**, one message each; a nested or repeated value's key is its path joined with dots (`content.year`, `sources.0`), the same as the control's `name` in the `FormData`. An error from `errors` is the answer to a submission, so it **shows at once**, touched or not, and in the server HTML; it **hides on its control's next edit** (an `input` or `change` from a control with that `name`) and all hide on a reset, until the app passes a new object. A Field's own `error`, shown once touched, is for checks as the user types, and wins the message once touched. `errors` is held in a memo, so an object written inline is the same until a value in it changes. No error from outside blocks a submission.
  - **A blocked submission:** on `submit`, Form calls `checkValidity()`, which fires `invalid` at each invalid control (touching its Field) and shows nothing; if it fails, Form cancels the event, skips `onSubmit` and focuses the first invalid control in tree order, a Menhir control's hidden input handing focus to its button. A submitter with `formnovalidate` skips the check. A router that intercepts submissions on the document checks `defaultPrevented`, as Solid Router's does.
  - **`novalidate` is set once hydrated,** not in the server HTML: before hydration the browser validates a submission with its own bubble; after, the Fields show the errors.
  - **Submission is Solid's:** `onSubmit` is the native handler with the `SubmitEvent`, called only when not blocked (an exception to "Nothing cancels the part's handler": a blocked submission is no submission), and Form never cancels a valid submission, which a router's form action and a post to the server need. A client-side submission cancels it and calls an `action(...)`. The pending state is the router's `aria-busy` on the form, or a `createOptimistic(false)` flag the action sets, as the cheatsheet builds a process flag; Form holds none.
  - **A schema's issues become `errors` through a util of its own,** `issuesToErrors` in `menhir/form/standard-schema` (230 B), so a Form without a schema does not bundle it (`test/bundle-size/formModules.test.ts`). It reads the Standard Schema `Issue` (`message`, `path`), whose shape it declares for itself, so it serves every schema library that implements the interface and depends on none; it is tested against two (devDependencies). The first issue on a path wins; an issue with no path goes under `""`, which no Field reads and the app renders itself.
- **Fieldsets** (decided on 2026-11-24 with Fieldset, #145; `src/fieldset/README.md`). **Not a component: a recipe** on Field's docs page. The WAI tutorial on grouping controls and the HTML standard on the fieldset element decide it.
  - **A native `<fieldset>` and `<legend>`** give the `group` role and its name in the server HTML, and `disabled` on the fieldset disables every form control inside it but those in its first legend, Menhir's buttons and hidden inputs included ("Form controls are native buttons"): no press, no focus, no form data, no validity. `:disabled` matches the fieldset and each control it disables, so no part adds `data-disabled`; putting it on a control's own parts would need every control to read a context, which Field rejected for the same reason.
  - **A group with one description and one error is a Field whose Control is the fieldset:** `<Field.Control render={(p) => <fieldset {...p} />}>`, with a native `<legend>` in place of `Field.Label`, which cannot name a fieldset. The fieldset gets `aria-describedby` naming the Description and the shown Error, `aria-invalid`, the Field's `data-*`, its `name` (the key of a Form's error) and `disabled`; the Field reads the validity of every control in the group and tracks touched for the whole group, with no change to Field. A rule the browser has no constraint for, such as "at most two" checkboxes, is an error from outside; "at least one" is Checkbox Group's `required` ("Checkbox groups" below).
  - **A group of Fields, such as an address, is a plain `<fieldset>`**, each Field with its own error: a Field around them would take the first invalid inner control as its own.
  - **Checkbox Group (#146) and Radio (#147) render their own root,** which joins a Field as its Control, as the fieldset does here; whether that root is a `<fieldset>`, a `group` or a `radiogroup` is theirs to decide against their WAI-ARIA patterns.
- **Checkbox groups** (decided on 2026-11-24 with Checkbox Group, #146; `src/checkbox-group/README.md`). Several checkboxes that hold one list of values: the WAI-ARIA checkbox pattern and its mixed-state example.
  - **Built on Checkbox** (section 6, rule 4, `simpleBases`): `Root` renders a `<fieldset>`, named by a native `<legend>` inside it, as the Fieldset recipe has it; `Item` and `Parent` render `Checkbox.Root`; `Indicator` is Checkbox's, re-exported. Checkbox reads nothing of the group.
  - **The value** is `value`, `defaultValue` and `onValueChange` on the Root, an array in every mode, `[]` when empty; a box checked is added at the end, and values with no Item are kept. Each Item takes a `value` and is checked while the list has it.
  - **What the form receives:** one entry per checked box under the group's `name`, from each Item's hidden input, which takes the group's `name` and `form`; the Parent submits nothing.
  - **The Parent is a part** over the `values` it is given, not Items that register, so its state is right in the server HTML and an Item pays nothing for it: checked while the list has all of them, mixed while some. A click on a mixed Parent checks all, on a checked one unchecks all, and on an unchecked one brings back the combination the user made last, or checks all when that is none, as the mixed-state example does; the Parent's own changes leave the combination as it was.
  - **`required` means at least one:** a visually hidden `<input type="radio">` after the fieldset, never checked, is `required` while the list is empty, so the browser blocks a submission with its message for a missing selection ("Please select one of these options.") and focuses it, and it hands focus to the first enabled box. Browsers find a radio missing only when it has a name, so it takes a unique one from `createUniqueId`; unchecked, it submits nothing. No box is `required` or `aria-required` itself; the Root has `data-required`. Its `required` follows the list, which a form reset does not change behind the binding's back. It counts the list, not the form's data: a checked box that is disabled satisfies it unsubmitted, so a box that must stay checked and be submitted is `readOnly`.
  - **`disabled`** on the Root disables the fieldset, and every Item and the Parent through the group's context, so each box and its Indicator get `data-disabled`; on an Item, that box alone.
  - **The group's error** is a Field's, with the group as its Control (`<Field.Control render={CheckboxGroup.Root}>`): Field reads the hidden radio's `valueMissing`, and the fieldset gets the Field's description, error, `name` and `disabled`. The browser's message names no group, so the docs give the Error `match="valueMissing"` and the app's words.
  - **A form reset** sets the list back to `defaultValue` once, through the setter; each Item passes its Checkbox a `defaultChecked` equal to its state, so Checkbox's own reset asks for nothing.
- **Radios** (decided on 2026-11-24 with Radio, #147; `src/radio/README.md`). A group of radio buttons that holds one value: the WAI-ARIA radio group pattern.
  - **One entry point, `menhir/radio`, with `Root`, `Item` and `Indicator`:** a radio means nothing outside its group, so the group is the Root. `Root` renders a `<fieldset role="radiogroup">`, which ARIA in HTML allows, named by a native `<legend>` inside it, so the name is in the server HTML; `Item` a `<button type="button" role="radio">` and its hidden input; `Indicator` a `<span>` with its Item's `data-*`. It imports only `core`.
  - **The value** is `value`, `defaultValue` and `onValueChange` on the Root, the checked Item's `value`, `null` while none is checked; `onValueChange` gets `null` only from a form reset to no `defaultValue`.
  - **The keys:** one tab stop on the checked radio, else the first enabled one ("A group of items is one tab stop"); every arrow key moves focus and checks, Right and Down to the next enabled radio and Left and Up to the previous, wrapping, Left and Right mirrored right to left; no Home or End, as the pattern and native radios have none. `core/rovingFocus.ts` reads one axis, so the Root sets it from each key and the module did not change. Space checks; Enter is canceled, as on Checkbox. The toolbar model, where arrows move without checking, is left out.
  - **What the form receives: one hidden `<input type="radio">` per Item** under the group's `name`, each clicked by its button, so the form sees native `input` and `change` events and `form.elements[name]` is a `RadioNodeList`. A controlled group that declines a change checks its checked Item's input again after the flush, since the browser unchecked it. One input for the group would fire no `change` from one checked radio to another.
  - **`required`** is the browser's: every hidden radio is `required` while none is checked, so the browser's message for a missing selection shows and it focuses the first enabled radio. A group with no `name` gives its inputs a `createUniqueId` name while none is checked, since browsers find only a named radio missing; once one is checked they have none, so it never submits. The Root has `aria-required` and `data-required`; an Item neither.
  - **`disabled`, a form reset and a Field** work as for Checkbox Group: the fieldset is disabled and every Item through the group's context; a reset asks once, since every Item's input asks the group and a set equal to the turn's last does nothing; the group joins a Field as `Field.Control`'s `render`.
  - **The hidden input moved to `core`** (`hiddenInput.tsx`), shared by Switch, Checkbox and Radio's Items, as a function with positional parameters: a component's props, or an options object, cost Switch and Checkbox 50 B to 110 B each, where positional parameters cost 30 B (measured on 2026-11-24; `src/radio/README.md`, "Size").
  - **Menu's `RadioGroup` and `RadioItem` share nothing more** than `createControllableSignal`: a menu's radio item is in a popup, checked by activating it, moved to by list navigation, and has no hidden input.
- **Number fields** (decided on 2026-11-24 with Number Field, #149; `src/number-field/README.md`). A text input for a number with buttons that step it: the WAI-ARIA spinbutton pattern and its quantity example.
  - **The user's element is not an `<input type="number">`, and the form's is.** A number input formats nothing the page chooses, makes text that is not a number `""` without saying what was typed, changes on the wheel in some browsers and draws its own spin buttons. So the user types in an `<input type="text" role="spinbutton">`, and the Root renders a visually hidden `<input type="number">` after its `<div>`, with the plain number, `name`, `form`, `min`, `max`, `step`, `required`, `disabled` and `readonly`: `FormData`, constraint validation, the browser's messages and Field work as for a native number input. A user's change writes it and fires its native `input` and `change`, so a Field's touched state and a Form's error under its name follow; a declined change is put back after the flush, as a Select's input is.
  - **Parts:** `Root` (the `<div>`, which holds the value), `Input` (the spinbutton), `Increment` and `Decrement` (`<button type="button" tabindex="-1">`, out of the tab order as in the example, with `aria-controls` naming the Input, natively `disabled` at their limit or while the field is disabled or read-only, and no name of their own). It imports only `core`.
  - **The value** is `value`, `defaultValue` and `onValueChange` on the Root, a number, `null` while empty, with no details argument. The user's changes are clamped to `min` and `max`; an app's value is shown as it is, and the hidden input reports it.
  - **Typed text is committed on blur and on Enter**, not on each key: half-typed text is often not a number, and reformatting it would move the caret. A commit reads the text, rounds it to the digits the format shows, clamps it, and shows the value formatted again; text that is not a number goes back to the value's. A typed value off the step grid is kept, and the browser's `stepMismatch` reports it; without a `step` the hidden input's is `any`, so a typed decimal, such as a price, is valid while the keys step by 1. Text the user did not edit is not read again.
  - **`format` and `locale`** as Meter takes them, with `Intl.NumberFormat`; parsing reads the formatter's own parts (the locale's digits, decimal, minus sign and group, and the currency, percent, unit and literal text it writes) in `parse.ts`, about 280 B, which the Root bundles, since an Input that can be typed in needs it.
  - **Keys** as the pattern says: Up and Down by `step` (default 1), Page Up and Page Down by `largeStep` (default ten steps), Home and End to `min` and `max` only when set, else the caret's. A step lands on the grid from `min`, else 0, as `stepUp()` does, rounded to the decimals of `step` and `min`. Modifiers and Shift with an arrow are the browser's.
  - **The buttons never take focus:** they cancel `pointerdown`, a mouse press focuses the Input and a touch focuses nothing. A pointer press steps, then repeats after 400 ms every 60 ms until released or at the limit; a click with `detail` 0, from a screen reader or voice control, steps once.
  - **It joins a Field with the Root as `Field.Control`'s `render`**, as a Radio does: the Root hands the Field's `id`, `aria-describedby` and `aria-invalid` to the Input, generates the Input's `id` otherwise, so the Input takes none ("Generated ids belong to the root"), and its `disabled` reaches every part.
  - **The Input's text is the `value` attribute**, bound as `defaultValue`, and written as a property only when the value changes: a bound `value` is written again whenever another attribute of the element changes, such as a Field's `aria-invalid`, which threw away what the user had typed (Solid's `UNCOMMITTED_INPUT_OVERWRITTEN`, found with this component).
  - **Elements a part needs only in its handlers are plain fields of the Root's context**, as Select's Trigger, input and Popup are: the Input sets `input` from its ref and an `edited` flag on each edit, and the Root and the buttons read them in event handlers and `onFlush` callbacks. Not a slot (`core/slot.ts`), which makes a mounted part's value reactive for something that renders from it; nothing renders from these (decided on review, #149).
- **Sliders** (decided on 2026-11-25 with Slider, #148; `src/slider/README.md`). A value picked along a range by moving a thumb: the WAI-ARIA slider pattern.
  - **The control is a native `<input type="range">`, visually hidden inside the Thumb, and what the user sees is the page's own elements.** The input gives the `slider` role, `aria-valuenow`, `aria-valuemin` and `aria-valuemax` from its `value`, `min` and `max`, a name from a `<label for>`, focus, `disabled`, `FormData` and the reset, in the server HTML. It cannot be styled but through each engine's pseudo-elements (no engine had the standard `::slider-thumb` on 2026-11-25) and holds no children, so the track, the filled part and the thumb are `<div>`s the consumer styles. Not a `role="slider"` element by hand, which would rewrite what the input gives and need a hidden input beside it.
  - **Parts:** `Root` (a `<div>` that holds the value), `Track` (the `<div>` that takes the pointer), `Thumb` (the `<div>` around the input) and `Value` (a `<span>` with the value's text, as a Meter's). **No Indicator part:** the filled part carries no state the Root does not, so it is a plain element sized with `--slider`, as a Meter's bar is ("A value along a range" above). It imports only `core`, and not `core/range.ts`, whose `role` and `aria-value*` a range input has natively and ARIA in HTML says not to write on it.
  - **The value** is `value`, `defaultValue` and `onValueChange` on the Root, a number, never `null`; without a `defaultValue` it starts at the midpoint of `min` and `max`, as a range input does. **`onValueCommit`** is called once the user has finished a change: a drag released or canceled, a key released (a held key commits once) or focus leaving first, a form reset once taken; changes that overlap, such as a key during a drag, commit once. A change the input makes itself, as assistive technology may, is taken as the user's, and committed on its `change`. The input fires its native `input` on each change and `change` on each commit, as a range input does under a drag, so a Field and a Form follow.
  - **`min`, `max` and `step`** default to 0, 100 and 1, as the input's, and go on it. A value the user sets lands on the step grid from `min`, and the last value is the grid's last at or under `max`, as the input's sanitization has it; steps are rounded to the decimals of `step` and `min`.
  - **Keys** as the pattern says, on the input, each canceled so the input does not move itself: Right and Up by `step`, Left and Down back, Left and Right swapped right to left, Page Up and Page Down by `largeStep` (default ten steps, as Number Field's), Home and End to the ends. With Ctrl, Alt or Meta held, the browser's.
  - **The pointer is the Track's:** a primary press moves the thumb there and focuses the input, a captured drag follows the pointer, a press on the thumb keeps its distance from the centre, `touch-action: none` keeps a touch drag from scrolling the page, and the Track cancels `pointerdown`, so nothing is selected. Vertical runs from the bottom up, right to left from the right.
  - **`--slider`** on the Root is the value's percentage of the range; the consumer places the thumb with `inset-inline-start`, which mirrors right to left by itself, so neither direction nor orientation needs a prop for the look. `orientation="vertical"` gives the input `aria-orientation="vertical"`, and every part `data-vertical`, else `data-horizontal`.
  - **The value's text:** `format` takes `Intl.NumberFormat` options, as Meter's does but formatting the value itself by default, or a function `(value) => text` for text that is not a number; the text is the input's `aria-valuetext` and the Value's content.
  - **It joins a Field with the Root as `Field.Control`'s `render`,** as Number Field and Radio do, not with the Thumb as #148 first had it: the Field's `disabled` must reach the Track and its `name` the input. The Root hands the Field's `id`, `aria-describedby` and `aria-invalid` to the input; a range input is never invalid, so a Field shows only errors from outside. `test/bundle-size/fieldModules.test.ts` checks that `menhir/slider` bundles no module of `src/field`.
  - **Two thumbs are left out** until asked: a range has a value of another type, an array, a thumb's bounds that follow the other's value, the choice of thumb a press moves, and a group with a label per thumb in a Field. It would be another Root, whose `onValueChange` takes an array, and a Thumb part that keeps two apart, which one thumb does not ship (section 6, rule 6).

The helper, built in #13: `core/renderElement.tsx`.

```tsx
import type { JSX } from "@solidjs/web";
import { untrack } from "solid-js";

/** The props a part hands to its element, or to `render`. */
export type ElementProps = Omit<JSX.HTMLAttributes<HTMLElement>, "ref"> & {
  ref?: (element: HTMLElement) => void;
};

export type RenderProp = (props: ElementProps) => JSX.Element;

export function renderElement(
  props: { render?: RenderProp },
  elementProps: ElementProps,
  fallback: RenderProp,
): JSX.Element {
  const Render = untrack(() => props.render) ?? fallback;
  return <Render {...elementProps} />;
}
```

A part calls it last:

```tsx
export function SwitchRoot(props: SwitchRootProps) {
  // own: role, aria-checked, data-*, handlers, ref.
  const elementProps = mergeElementProps(own, omit(props, "render", "checked"));
  return renderElement(props, elementProps, (p) => <button {...p} />);
}
```

- `ElementProps` is typed for `HTMLElement`, not for the default element, so that it spreads onto any tag. Its `ref` is narrowed to a callback: `Ref<HTMLElement>` also allows a variable and an array, which makes it unassignable to `Ref<HTMLButtonElement>`, and `<button {...props} />` then fails to type-check. The part composes the consumer's ref and its own into that one callback.
- A part's public props are `JSX.HTMLAttributes<HTMLElement>`, its own props and `render?: RenderProp`. Attributes of a specific element are typed by the consumer's own JSX inside the render function, so parts need no generics.
- Parts whose default element is not an HTML element (an SVG part) need a second `ElementProps`; decide when the first one appears.
- No budget of its own: the helper is about 80 B minified, and its cost is counted in the budget of every entry point that uses it.
- Inlining the two lines in each part measured the same as calling the helper. The helper is preferred because it is the one place to add a state argument or a dev warning.
- Spread cost, measured in #13 (jsdom, counting attribute writes and getter reads; 2026-11-19). A part with two own attributes and a consumer `title`, built three ways: all props through the merged spread; own attributes written in JSX with the consumer's props spread; no spread at all. In all three, changing one value re-read every dynamic attribute of the element once and wrote only the changed ones. Writing own attributes in JSX next to a spread kept nothing separate, so parts keep them in the merge. Calling the merge inline in the spread gave the same writes but ran the merge again on every change. Timing was not measured, nor a spread over a store, whose keys can change.
- Tests (`src/core/renderElement.test.tsx`, `test/core/renderElement.hydrate.test.tsx`): the default element, another tag, a component; `render` passed as an expression is read once without a diagnostic; server render then hydration adopts the element in all three cases, and when the render function calls `dynamic` itself, with nothing logged; a handler, a `class` and a ref written before and after the spread, to pin down the rule above; a type test that `ElementProps` spreads onto `a`, `button` and `input`.

### What the browser does for popups

Decided on 2026-11-22 (#94; ADR 0006), for the browsers of section 5. Support was checked that day in `web-features` 3.47.0 and browser-compat-data 8.1.10. The spike built a modal dialog and an anchored non-modal popup twice, once on the platform and once by hand, and ran the same keyboard, focus and pointer cases against both in Chromium 159, Firefox 159 and WebKit 27.2. The engines agreed on every case except three, named below: where Shift+Tab goes from a modal dialog's first element, the exit transition, and where focus is after a refused Escape on a popover. The spike's code is not kept in the repository; the cases and results below are its record.

| Feature                                          | Baseline on 2026-11-22                          | Decision                                                                                                                    |
| ------------------------------------------------ | ----------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| `<dialog>` with `showModal()`                    | Widely available (since 2024-09-14)             | **Use** for Dialog and Alert Dialog                                                                                         |
| `popover` (`auto`, `manual`) and `popovertarget` | Newly available (2025-01-27); Widely 2027-07-27 | **Use**, as section 5's exception: `auto` for Popover and the menus, `manual` for Tooltip and Combobox; not Navigation Menu |
| `popover="hint"`                                 | Not Baseline (no Safari release)                | Do not use; Tooltip is `manual`                                                                                             |
| `inert`                                          | Widely available (since 2025-10-11)             | **Use**, not `aria-hidden`, if a modal popup is ever not a `<dialog>`; `showModal()` makes the page inert itself            |
| The top layer                                    | With `<dialog>` and `popover`                   | **Use**; no portal                                                                                                          |
| CSS anchor positioning                           | Not Baseline (no Firefox)                       | Do not use; `@floating-ui/dom` stays (section 5)                                                                            |
| `CloseWatcher`                                   | Not Baseline (Safari 27.3 is in beta)           | Do not use; a modal `<dialog>` and an `auto` popover already answer close requests                                          |
| `closedby`                                       | Not Baseline (Safari 27.3 is in beta)           | Do not use; outside press is written                                                                                        |
| `requestClose()`                                 | Newly available (2025-05-27)                    | Do not use                                                                                                                  |
| `commandfor` / `command`                         | Newly available (2025-12-12)                    | Do not use                                                                                                                  |

No feature is used "where supported, with a fallback": the fallback would be the code the feature was meant to save (section 6, rule 6).

**Navigation Menu is not one of "the menus"** (decided on 2026-11-23, #105; amended in ADR 0006). Its Panels are in the page's flow, `hidden` while closed, as Collapsible's are, and the consumer's CSS places each under its Item, as the WAI-ARIA disclosure navigation example does. A top-layer panel would need `floating/positioning` (about 7 kB gzipped) to be placed under its Trigger, and an `auto` popover opened on hover would close the page's other popovers. So it bundles no positioning, no presence and no top layer; Escape, a press outside and focus leaving are its own to write, with `dismissal/escape.ts` and a few lines. An ancestor with `overflow: hidden` can clip a Panel, as it can any dropdown in a page.

What `<dialog>` with `showModal()` did in all three engines, and what is left to write:

- **Done by the browser:** the top layer (above a `z-index: 9999` element), an inert page (a script cannot focus outside it, and Chromium's accessibility tree leaves the outside out), Escape (as a `cancel` event), initial focus on the first focusable element, return focus to the element focused before, nested dialogs closing one Escape at a time with focus returning step by step, `::backdrop`, and close requests, which include the back gesture on Android (HTML standard, "Close requests and close watchers").
- **Left to write:**
  - **Controlled state:** an effect calls `showModal()` and `close()`.
  - **Outside press:** a press on the `::backdrop` targets the `<dialog>` element itself. It closes only if the press both started and ended there, so a text selection dragged out of the dialog does not close it.
  - **The Tab wrap.** The browser lets Tab leave the last element for the browser's own UI, and Shift+Tab from the first. The WAI-ARIA pattern says "Tab and Shift + Tab do not move focus outside the dialog" (read on 2026-11-22), and it outranks size (sources above). The spike's version, a keydown handler over a tabbable search, made Tab and Shift+Tab cycle inside the dialog in all three engines. Without it, Tab from the last element went to the browser's UI in all three, and Shift+Tab from the first went there in Chromium and to the `<dialog>` itself in Firefox and WebKit. Built in #27 as `floating/focus/tabWrap.ts`.
  - **A refused Escape is held only once.** The spec makes `cancel` cancelable only with history-action activation. In all three engines the second Escape fired a `cancel` that could not be prevented, then `close`, even with a click inside the dialog between the two. A controlled Dialog that keeps its state at `true` calls `showModal()` again from `close`; it stays modal and focus stays where it was. Dismissal (#26) reports that close once, not twice.
  - **Scroll lock:** the page still scrolls behind a modal dialog in all three. `html:has(dialog:modal) { overflow: hidden }` stopped it in all three with no script; #28 starts from there. Built in #28 as `floating/scroll-lock/scrollLock.ts`: the same declaration as an inline style on `<html>`, set only while a modal popup that imports it is open, plus the padding for the scrollbar it takes away.
  - **Exit animations:** a CSS-only exit transition ran only in Chromium (`overlay`). Firefox and WebKit removed the dialog at once. Presence (#96) keeps the dialog open while it animates, then calls `close()`.
- **Constraints it brings:**
  - **The Popup part is a `<dialog>`.** A `render` function must return a `<dialog>`, since `showModal()` exists on no other element; a development build can check it.
  - **Server HTML can only say `<dialog open>`,** which is a non-modal dialog: the page stays focusable until hydration, and `showModal()` throws `InvalidStateError` on it, so hydration calls `close()` first. Dialog (#31) renders a `defaultOpen` dialog closed on the server instead ("API conventions", "Popups").

What `popover="auto"` with `popovertarget` did in all three engines, rendered in place after its trigger:

- **Done by the browser:** the top layer (not clipped by an `overflow: hidden` ancestor, above a `z-index: 9999` element), light dismiss by a press outside, Escape, return focus to the trigger on Escape, `aria-expanded` on the trigger (Chromium's accessibility tree), Tab from the trigger into the popup and from its last element on to what follows the trigger, a press on the trigger closing it without reopening, and nested popovers closing one at a time.
- **Left to write:**
  - **Controlled state:** the `toggle` event reports the change. `beforetoggle` cannot be cancelled on close, so a controlled popover that refuses a close is shown again: in a microtask in the spike, and on `toggle`, once the popover is hidden, in dismissal (#26), since with real input a microtask runs inside the browser's hide. After an Escape, focus has already moved to the trigger in Chromium and Firefox; WebKit left it in the popup.
  - **The reason for the close.** One `toggle` event covers Escape, outside press and a trigger press. Dismissal (#26) tells them apart with its own Escape and pointer listeners.
  - **Positioning:** `@floating-ui/dom` with the `fixed` strategy, which is what the top layer is.
- **Constraints it brings:**
  - **`popovertarget` needs an id on the popup.** The root's generated id provides it ("Generated ids belong to the root").
  - **A closed popover is `display: none`** in the browser's own stylesheet, so server HTML with `defaultOpen` stays hidden until hydration calls `showPopover()`. Popover (#33) renders it closed, as Dialog does, and hydration shows and places it.
  - **Nesting follows the document tree,** or the `popovertarget` invoker. `showPopover({ source })` is not Widely available.
  - **Focus returns only for the first popover of a stack** (HTML standard, the show popover steps): a popover nested in another, closed with focus inside, leaves focus on the `<body>`. Popover (#33) returns it to its own Trigger when focus was inside as it closed, which it reads on `beforetoggle`.
  - **Focus leaving does not close it:** Tab from the popup's last element to the page left it open in all three. A `manual` popover stayed open when an `auto` one opened and on a press outside, so Tooltip neither closes nor is closed by a Popover.

Sizes, measured as `test/bundle-size` measures (Rolldown through Vite 8, minified, gzipped, Solid left out with its production constants). Each is an app that renders the prototype, less an app with only a button (257 B). The hand-built prototypes are lower bounds: no radio groups or shadow roots in the tabbable search, no iOS handling, no padding for fixed elements in the scroll lock.

| Prototype                                                                          | Platform | By hand |
| ---------------------------------------------------------------------------------- | -------- | ------- |
| Modal dialog: controlled, Escape, outside press, initial and return focus, nesting | 487 B    | 1,130 B |

## 10. Definition of done, per component

- Its test suite, assembled as section 8 describes, passes in jsdom and Chromium. Cases left out are listed with a reason.
- Keyboard and screen-reader behaviour matches the WAI-ARIA pattern.
- No Solid dev diagnostics are reported while its tests run. `createRenderer` enforces this for every test.
- Works with SSR and hydration.
- Size budget set and met; only allowed layers imported.
- Docs page with an unstyled example and the measured size.
- A working example on the home page, linked to its docs page and tested in `website/src/Home.test.tsx`.
- A row on the bundle-size page's comparison: each library in `test/bundle-size/comparison.ts` that has the component maps it to its module.
- Its sources are recorded (section 8), and which browsers and screen readers it was tried with.
- A changeset (AGENTS.md, "Changesets").

A module of the `floating` layer has no entry point, so no budget and no docs page of its own. It is done when:

- Its test list is in its README, with the cases left out and a reason for each, and its tests pass in jsdom and Chromium.
- No Solid dev diagnostics are reported while its tests run.
- It works with SSR and hydration: nothing reads `document` or `window` at import time or during a server render.
- A popup that does not use it does not bundle it, and its measured size is in its README (#95 decides how it is measured).
- It imports only what the `floating` layer may (section 6, rule 4).
- Its sources are recorded, and the decisions made on it are in this plan.

## 11. Risks

| Risk                                           | Mitigation                                                                                                                                                |
| ---------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Solo maintainer burnout                        | Narrow scope; announce after Phase 2; no promise of full parity.                                                                                          |
| WAI-ARIA patterns change                       | Record the date each component's pattern was read and check it at each release, as section 8 describes.                                                   |
| React patterns leak in                         | Section 8 puts Solid 2.0 idioms first, and no library's source is translated. The diagnostics line in section 10 catches React-shaped effects.            |
| Solid 2.0 ecosystem and tooling still settling | Keep dependencies minimal; isolate 2.0-specific code in `core`.                                                                                           |
| Duplicating an existing Solid 2.0 library      | Differentiate on size and Solid-native design; measure Switch against the existing libraries and revisit before Phase 2 if Menhir is not clearly smaller. |
| Size creep                                     | CI budgets and published numbers.                                                                                                                         |

## 12. Open questions

1. ~~Build Menhir, or contribute to an existing port?~~ Decided on 2026-11-19 (#1): continue with Menhir, as a size-first library with its own design. Reasons in section 4; the size check that would reverse this is in section 11.
2. ~~Polymorphism: an `as` prop, a render function prop, or both?~~ Decided on 2026-11-19 (#11): a `render` function prop, and no `as` prop. An `as` prop that takes a tag name adds 1.6 kB gzipped of Solid's runtime to every app. Details in section 8 ("Polymorphism").
3. ~~Package shape~~ Decided: one `menhir` package with a subpath export per component, as in section 6 ("Package shape").
4. Public API conventions: part names, controlled-state props and `data-*` attributes. Follow an existing library's, or Menhir's own? Matching a library makes its styled layers and docs easier to port; Solid 2.0 idiom wins where they conflict (section 8). Decided on 2026-11-20 (#12), and generated ids on 2026-11-21 (#22): section 8, "API conventions". Menhir's own part names and `data-*` attributes, `on<State>Change` callbacks with the value only, native buttons for form controls.
5. ~~Is the `solid` export condition still needed in 2.0?~~ Decided on 2026-11-19 (#6): yes. The 2.0 library guide prescribes it, and an SSR app fails without it. No separate server build. Details in section 6.
6. ~~Test stack~~ Decided: Vitest 5.1, jsdom plus Chromium, `@solidjs/testing-library`, as in section 7.
7. ~~Tooling~~ Decided: follow the `pnpm create solid@latest` template (oxlint, TypeScript 7, `@solidjs/testing-library`).
8. ~~Which browsers are supported, and how much of a popup the browser does?~~ Decided on 2026-11-22 (#94; ADR 0006): Baseline Widely available, plus `popover` (section 5, "Browsers"). Details in section 8, "What the browser does for popups".
9. Is the `floating` layer internal, as `core` is, or does it get entry points for apps and styled layers that build their own popups (#95)?
10. ~~May a popup import another popup?~~ Decided on 2026-11-22 (#32): a popup may import the popup it builds on, named in `popupBases`, and no other (section 6, rule 4). The answer also serves Context Menu, Menubar and Autocomplete, which builds on Combobox (#104).
